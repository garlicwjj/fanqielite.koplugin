# 从零到一

## 2026-09-26：长目录按序号直接跳转

长书目录分段把万章菜单控制到最多 100 个章段，但定位第 5555 章仍要先判断所属章段再翻页。超过 200 章的书籍详情现在增加“跳到指定章节（共 N 章）”，输入 1 到 N 的目录位置后复用既有 `open_chapter()`；已缓存章节保持离线打开，未缓存章节仍走同一联网、取消、超时、解析和保存边界。

输入阶段不写设置、不改当前章。提交时重新查找书籍并比较目录长度，书籍已移除、目录变化、空值、控制字符、小数、非数字和越界序号都固定停止；只有仍有效的整数才关闭输入框并打开章节。合成测试覆盖 250 章跳转、200/201 显示边界、目录缩短和书籍移除；PW3 数字键盘、长书弹窗宽度、联网跳转和墨水屏返回体验仍待实机验证。

## 2026-09-26 非空书架保留可见添加入口

首页原先只在空书架时把“搜索或添加一本书（推荐）”放在顶部；一旦已有书，三个添加/导入入口都会排到全部书籍之后，长书架中添加下一本书需要翻到末页。现在非空书架把常用的“搜索或添加”固定放在排序项之后、书籍列表之前，因此即使最近阅读同时显示继续、上一章和下一章，它也最多是第 5 项。文件导入和尚未开放的扫码仍保留在书籍列表之后，避免三个低频入口一起挤走日常切书区域；空书架首次使用顺序不变。

书籍行此前把从未打开的新书显示成 `[1/总章数]`，外观上像已经读到第 1 章；现在未读且已有目录的书明确显示 `[未开始 · 共 N 章]`，只有存在本机打开记录或已验证导入进度时才显示 `[当前/总章数]`，无目录仍显示 `[待获取目录]`。首页契约测试分别先复现入口沉底和未读状态误导，再锁定新顺序、未读/已读文案、排序、书籍回调及原有首次流程。

这些结果来自合成菜单测试，尚未证明 PW3 一屏实际容纳数量、分页手感、文案宽度或残影表现；进入稳定候选前仍需真机和陌生新手验证。

## 2026-09-26 兼容矩阵候选清单门禁

30 本／90 场景的正式矩阵此前只有最终证据门禁，若先随意读取章节，可能到最后才发现目录长度档位、完结/连载或男频/女频/出版覆盖不足。新增开发工具 `tools/compatibility-candidates.js`，在发起三章取样前校验恰好 30 本的匿名候选清单；它只接受日期、与 ID 对应的番茄官网书籍页、目录章数、连载状态和分类，不接受书名、作者、简介、正文或额外字段。CI 合成测试覆盖五档 5/5/8/7/5、12/18 连载配额、分类缺口、重复 ID、官网地址绑定及不完整清单失败。

这只是防止取样计划配额错误，不是新增真实兼容样本，也不证明页面元数据、解析、缓存或 PW3 显示通过。真实候选清单在采集日仍须人工复核且不提交仓库；正式完成状态继续只由候选提交上的 30 本／90 场景证据和真机结果决定。

## 2026-09-21 浏览器导出结果的完整性提示

浏览器工具原本允许在未观察到官方进度请求时导出仅含书架的文件，也允许某本书没有作者，但成功提示只说“已导出 N 本”，容易被误认为完整进度备份。现在成功提示只依据实际生成的白名单文件统计作者与最近阅读章节缺失数量，区分“页面未发现进度请求”和“已请求但部分书没有章节记录”，并始终说明章节内位置未导出。文件格式、官网请求和账号会话处理不变；合成浏览器测试覆盖两类提示与无进度请求时不会臆造请求。作者与真实已读进度仍需专用测试账号验证，此改动不证明字段已完整获取。

## 2026-09-21 官网公开入口只读烟雾检查

匿名从[番茄官网排行榜](https://fanqienovel.com/rank/1)选取当前公开的[255 章书籍页](https://fanqienovel.com/page/7654593151348247614)与[1936 章书籍页](https://fanqienovel.com/page/7320218217488600126)。只读请求详情页和官方目录接口，不使用账号、不写 Kindle、不保存原始页面或正文。生产 `Parser.extract_initial_state()` 从前一本详情页提取状态成功；`page.bookId` 与请求 ID 一致，`bookName` 和 `author` 均为字符串，未观察到私用区字符。其目录响应 `code=0`，`chapterListWithVolume` 为 1 个卷数组、包含 255 个章节对象，`allItemIds` 也有 255 项。

本机现有 KOReader `rapidjson.so` 是 Kindle ARM 构建，无法在 macOS LuaJIT 中加载。因此桌面验证先用 Node 解析官网 JSON，再经不落盘的管道只投影原始 ID、标题与卷数组层级，交给生产 `Parser.book_from_state()`、`Parser.directory_from_payload()` 与固定取样器。255 章样本得到 255 章和 1／128／255 位置；1936 章样本的目录响应约 532,200 字节、5 卷，得到 1936 章和 1／968／1936 位置。两份目录标题均未观察到私用区字符。投影丢弃了其他响应字段，且未执行 Kindle 的完整 JSON 解码、缓存与显示链；不能据此宣称实机目录兼容。

对官网明确公开的[首章](https://fanqienovel.com/reader/7654593184701366846)只做一次内存中的正文解析检查：生产 `Parser.extract_initial_state()` 提取状态后，同样以长度帧管道传入原始章节 ID、标题、正文、权限和字数字段。`Parser.chapter_from_state()` 成功，得到 96 段、映射 1,115 个 PUA 字符，并在内存生成 7,885 字节 XHTML；没有保存或展示正文。它不证明人工校对无乱码、KOReader 渲染或缓存落盘成功，也不计入正式 30 本／90 场景矩阵。

同次对当前官方搜索路径仅发起一次无账号只读请求，得到空正文；没有返回可解析的书籍列表。它只说明此网络环境下这次搜索不可用，不能推断所有用户的搜索都会失败。实验版继续推荐粘贴官网书籍详情链接，不扩展对第三方或含混分享文本的解析，不绕过官网验证。

搜索的另一条可见分支此前把官网正常返回的零结果误标为“解析搜索结果失败”，且有结果时缺少就地修改查询入口。现在合法空列表独立显示“没有找到”的说明、本地数据安全状态和“重新输入 / 返回”；结果列表末尾始终提供“重新输入或粘贴官网链接”。真正的响应格式错误、空正文和安全验证仍走原有安全失败路径，不伪装成无匹配。失败优先测试覆盖空列表与两本结果的交互，以及已有书打开、新书加入仍按原路径；尚未在 PW3 实测弹窗大小、输入焦点与返回体验。

## 2026-09-21 调整为实验版快速迭代阶段

用户确认当前优先实现个人可用、操作顺滑的阅读主流程，暂不把每个罕见边界修复和正式发布级验收作为日常迭代前置。此阶段每个小改动仍保留可回退提交与针对性测试，改为每阶段一个 PR/CI 检查；真实兼容矩阵、PW3 全面回归、扫码安全审计和陌生新手五分钟安装留作稳定版候选门禁。书架/进度/缓存保护、凭证不落盘、官方内容与权限边界、插件写入范围、敏感设备操作先确认及不擅自发布 1.0 等底线不变。具体阶段规则见 [`QUALITY_PLAN.md`](QUALITY_PLAN.md)。

空书架首页原把未开放的扫码排在首位，推荐的可用添加入口排第二，第一次使用容易先点进无结果说明页。调整为“搜索或添加（推荐）→文件导入→扫码（尚未开放）”，已有书架的入口顺序保持不变。失败优先的首次使用契约测试先证实旧顺序不符合新阶段目标，再锁定首项能从官方链接加入书籍并开始阅读；尚待 PW3 和陌生新手验证实际菜单布局与操作时间。

文件导入后尚无目录的书籍原有主按钮写着“联网获取目录并开始阅读”，实际只保存目录并返回详情页，用户还需再点一次。现在目录保存成功后，从已更新的书籍记录取回当前章节，待目录网络操作结束再启动章节打开；有完整缓存时可复用，缺缓存时由既有公开章节流程继续联网。首次刷新不弹出中途成功提示，刷新失败则不会排队打开章节。失败优先测试覆盖原按钮的空转、导入位置恢复后的目标章节，以及第二次操作必须等待前一次网络操作结束。该合成验证不替代 PW3 上的联网提示、两个进度窗口和 ReaderReady 时序实测。

## 2026-09-20 设置替换后的最终校验恢复

设置原子写入会在临时文件同步、关闭和重读一致后才 `rename` 到主路径，并在替换后再次重读。旧实现把两个重读阶段当作同一种失败：若替换后的最终校验失败，`fanqielite.lua` 实际已经可能是新候选或异常文件，但 `save_state()`仍回滚内存并声称“上一版设置仍被保留”。这会让运行内存和磁盘分叉，也给出错误的数据安全承诺；原故障注入只覆盖改名前的同步、关闭、临时重读和改名失败，没有覆盖这一步。

持久化层现在从原子写入返回“是否已经替换主路径”。替换后校验失败时，先用已经验证并写入 `.old` 的上一版内存状态再次执行完整原子写入；恢复成功则返回明确的 `recovered` 状态，上层回滚内存并可如实说明旧版已经恢复。恢复写入或改名也失败时返回 `uncertain`：内存仍回滚，但普通保存和启动敏感字段清理都会说明磁盘主设置可能已改变，要求停止操作、重启并保留 `fanqielite.lua.old`。失败优先测试注入最终 `dofile` 异常、恢复成功和恢复改名异常，证明不回显 canary、不字符串化对象、成功恢复后主文件与 `.old` 都是上一版，以及无法恢复时不再作虚假承诺。断电、真实介质损坏和用户手工恢复仍须 PW3 演练。

## 2026-09-20 全局网络超时异常边界

KOReader v2026.03 的 [`socketutil:set_timeout()` 与 `reset_timeout()`](https://github.com/koreader/koreader/blob/v2026.03/frontend/socketutil.lua#L72-L86) 不只影响当前连接，还会改写模块级超时以及 LuaSocket/LuaSec 的全局 `TIMEOUT`。公开请求与未启用的一次性授权请求过去直接调用这两个框架函数：虽然 HTTP 请求本身已有 `pcall`，但设置或复位函数抛错仍会越过网络模块；若复位阶段失败，已经收到的响应还可能被继续处理，而后续联网处于未知超时状态。旧文档把“请求结束后调用复位”写成了“保证复位”，证据过强。

两个网络模块现在分别以固定边界配置和恢复超时。配置异常时不发起请求，并在返回固定提示前尽力执行一次复位；请求后的复位异常会丢弃响应，不读取或回显异常对象，公开通道明确说明本地数据未改变并要求重启 KOReader，敏感原型也停止返回成功结果。失败优先测试先复现两类异常逃逸，再用带 `__tostring` 的 canary 锁定不字符串化、设置失败不联网、尽力复位和复位失败不接受响应。该合成证据不能证明抛错后的 KOReader 全局状态已经恢复，因此提示不会建议原地重试；真机网络切换和框架故障仍待集中验证。

## 2026-09-20 ReaderReady 后消费导入位置

复核 KOReader v2026.03 固定源码发现，`FileManager:openFile()` 调用 `ReaderUI:showReader()` 后没有成功返回值；真正的文档打开位于后续 `UIManager:nextTick()` 协程。只有 ReaderUI 完成文档初始化并发出 `ReaderReady` 后，才会调用 `after_open_callback`。旧实现虽然用 `pcall` 防住同步异常，却在 `openFile()` 返回后立即清除浏览器导入位置；异步文档加载失败或 `GotoPercent` 回调异常时，位置已经不可重试。旧回调还属于即将关闭的 FileManager 插件实例，而 ReaderUI 初始化会加载新的 Fanqie Lite 实例。

现在排队打开只安装一次性 ReaderReady 回调，不消费导入位置。回调优先选择 `reader_ui.fanqielite` 的活动实例，重新核对同书同章待处理位置；随后才应用 `GotoPercent`，或确认已有 sidecar 应优先，最后清理并原子保存。位置应用异常不会回显对象或触发 `__tostring`；清理保存失败会恢复持久状态。测试覆盖排队未消费、ReaderReady 成功、位置应用异常、新实例接管、sidecar 优先、同步打开异常和清理保存失败。该证据依据 [FileManager v2026.03](https://github.com/koreader/koreader/blob/v2026.03/frontend/apps/filemanager/filemanager.lua#L1483-L1502) 与 [ReaderUI v2026.03](https://github.com/koreader/koreader/blob/v2026.03/frontend/apps/reader/readerui.lua#L579-L716)；仍需 PW3 验证真实异步失败、菜单切换及提示布局。

## 2026-09-20 章节缓存写入后的状态提示

联网打开章节的顺序是解析正文、原子写入缓存并执行上限淘汰，然后检查 KOReader `.sdr`、保存当前章，最后进入阅读器。旧错误文案只按最后失败步骤描述：如果缓存写入后 `.sdr` 检查异常，仍声称“书架、阅读进度和缓存没有改变”；如果设置保存失败，也只说明书架事务回滚，没有告诉用户新缓存已经存在。自动淘汰还可能已经删除较早缓存，因此这不是文案细节，而是错误的数据状态陈述。

章节准备函数现在接收明确的“本次缓存已写入”阶段标记和淘汰警告。已有缓存路径的失败继续说明三类数据未变；联网写入后的失败则说明新章节缓存已经写入、缓存状态已改变，书架和阅读进度未修改或已回滚，并提示较早缓存可能按 12 个上限清理。若自动清理部分失败，其固定说明也会保留。失败优先测试覆盖 `.sdr` 异常与设置写入失败，完整联网调用契约另证明阶段标记和清理警告传递到准备层；尚需 PW3 验证长提示分页和故障排除后的缓存复用。

## 2026-09-20 封面备份清洗

封面 URL 结构门禁落地后重新审计启动事务，发现旧设置中的不安全地址虽然会被 `Library.load()` 从当前书架移除，但敏感字段扫描只看键名，仍可能把加载前原值作为 `previous` 写入 `fanqielite.lua.old`。例如 `cover_url=https://...?...access_token=CANARY` 不会留在主设置，却可能残留在备份，违背“凭证不持久化”的边界。

持久化层现在对任意 `cover_url` 值复用 `safeurl.lua`：非空值必须通过同一套 HTTPS、权威部分、端口、控制字符和敏感查询键检查，否则按不安全启动状态处理。启动事务因此只把规范化后的安全状态同时写入主文件与 `.old`；直接写入器也会在创建任何文件前拒绝不安全候选或上一版。失败测试先证明旧实现漏检，再覆盖启动清洗、备份清洗、错误不回显 canary 和普通 `x-signature`/`x-expires` 兼容。该修复没有读取真实账号、浏览器会话或 Kindle 文件。

## 2026-09-20 封面 URL 凭证边界

浏览器导出器原先拒绝 URL 用户信息和片段，但仍会把 `?access_token=...` 一类敏感查询键写入 JSON；Kindle 端导入器与设置恢复更只检查 `https://` 前缀，带用户信息、空主机、片段、空白或异常端口的伪 URL 都可能进入设置。新增无网络依赖的 `safeurl.lua` 作为 Lua 侧共同门禁：验证 HTTPS 权威部分、主机、可选 1–65535 端口、百分号编码和控制字符，拒绝用户信息、片段以及解码规范化后包含授权、Cookie、CSRF、手机号、密码、session 或 Token 含义的查询键。浏览器侧使用 URL 解析器执行同一敏感键规则；普通 `x-signature` 与 `x-expires` 参数继续兼容，封面本身仍是可选字段。

失败测试先证明三条旧路径都会接受 canary，修复后覆盖明文/百分号编码 Token、用户信息、片段、空主机、空格、旧设置自动移除和安全 CDN 查询保留。错误只显示固定的“安全 HTTPS 地址”，不回显 URL 或 canary。该结构门禁无法判断被错误映射进普通路径、主机或无敏感键名参数的秘密值，因此不能替代真实响应字段审计；插件当前也不会主动下载封面。

## 2026-09-17 导入进度字段一致性

严格 JSON 导入过去分别验证 `current_chapter_title` 和 `reading_position`，却没有要求它们依附 `current_chapter_id`。只含标题或百分比的文件会通过确认和导入流程，随后因为无法构造 `imported_progress` 而静默丢弃这些字段，形成“提示成功但没有恢复进度”的假成功。现在只要标题或位置存在，就必须同时提供合法章节 ID；不含任何进度字段的纯书架记录继续有效，只有章节 ID、没有标题或百分比的记录也继续兼容，目录刷新后仍可按 ID 定位。失败测试覆盖标题与位置同时孤立、分别孤立、无标题进度及纯书架输入；现有浏览器导出、本地导出和一次性匿名管道都复用同一生产验证器。

## 2026-09-17 浏览器阅读进度完整性

当前公开前端包的 `GetReadProgressResponse` 把 `data` 声明为 `ApiItemInfo` 数组，书架页面会按 `book_id` 建立全局进度表；`ApiItemInfo` 声明章节 `item_id` 以及 `origin_chapter_title`/`title`，而旧导出器只尝试未被该模型证明的 `item_title`/`chapter_title`。旧实现还会静默跳过数字或畸形书籍 ID，以最后一项覆盖重复记录，并在导出书籍的章节 ID 无效时悄悄丢失进度。现在已发现的成功进度数组最多接受 500 项，每项必须是对象并包含 10–64 位字符串书籍 ID；本次导出书籍的记录必须唯一且含合法章节 ID。书架外的合法历史记录允许存在但不会进入文件，章节标题优先读取当前公开字段并保留旧字段兼容。失败测试先复现公开字段丢失，再覆盖畸形对象、数字 ID、重复记录、数字章节 ID、超限数组、书架外凭证 canary 排除及 Blob 创建前停止。

公开模型同时声明 `progress_rate`、`page_progress_rate` 和 `item_progress_rate`，但静态代码不能证明哪个字段代表当前章节内位置，也不能证明服务端使用 0–1、0–100 或其他量纲。本轮明确不把任何一个字段猜成导入格式的 `reading_position`；合成测试锁定即使三个字段出现也不输出百分比。真实已读书的脱敏类型与范围证据补齐后才能单独实现该映射，避免把整书进度错误应用到单章 XHTML。

## 2026-09-17 浏览器导出完整性门禁

浏览器导出器过去会静默跳过受支持书架中的数字或畸形 ID；详情接口漏项或缺少书名时还会生成“番茄书籍 + ID”的占位标题。这会把登录失效、响应截断或官网结构变化伪装成一次成功备份。现在书架响应必须是至多 500 项的连续数组，每个受支持小说条目都必须提供 10–64 位数字字符串 ID；详情响应必须与去重后的书架 ID 一一对应，且每本书都有非空、安全的书名。缺失、重复、额外详情、未知类型或畸形结构会在可选进度请求、Blob 创建和下载点击前固定停止，已存在的本地文件不会被这次脚本操作替换。

本轮只读获取了 2026-09-17 的公开书架 HTML 与前端包，没有登录、读取 Cookie 或调用账号接口。HTML SHA-256 为 `488a3a48ddfbdae1771c44e59280375d7002fd27ceee08373e36d8915762b86b`；书架包 `BookShelf.93e1261b.js` 为 `3c0ceb2b93656d7f48eeb717062e114f5bf6c71a4f04fbfb3460984040152e34`；公共包 `muye_a2c8e2a7.js` 为 `6ab30580f1dee8f57939998a18a300ddd9d366eee270541dde20b9b26b887973`。当前官网实现一次读取 `book_shelf_info`，随后把其中全部 `book_id` 传给 `/api/book/simple/info`；公开响应模型没有显示游标、`has_more` 或分页字段。因此没有凭空添加未知分页协议，而以严格一一对应门禁防止当前响应被静默截断。合成测试覆盖数字 ID、未知类型、详情缺失/重复、空书名、凭证 canary 及下载前停止；真实大书架、多页、已读进度和失效登录仍须专用测试账号验证。

## 2026-09-17 万章目录按需分段

上一轮允许最多 10,000 章后重新审计目录 UI，发现 `show_catalog()` 会立即为每一章创建菜单项和回调闭包。KOReader 2026.03 的 `Menu:updateItems()` 虽然只为当前页构造可见控件，但插件传入的完整 `item_table` 仍常驻内存；因此“解析不超限”不能证明老款 Kindle 打开万章目录时顺滑。现在 200 章以内保持一步直达，201 章起先按每 100 章显示章段，只有点入章段时才创建该段最多 100 个章节项；按 10,000 章解析上限计算，根菜单也最多 100 项。当前章所在章段和章节均标记 `[当前]` 并自动定位，`[可离线]`、`[缓存需修复]` 与绝对章节索引不变。失败测试先复现 1,000 章会生成 1,000 项，随后扩展到 200/201 边界、201 章尾段和 10,000 章上限；合成结果不能替代 PW3 的打开耗时、峰值内存、章段返回和墨水屏残影验证。

## 2026-09-16 超长目录资源上限

目录响应虽然受 1 MB 网络正文上限保护，解析器过去仍会遍历并保存响应中全部卷和章节；异常或未来变化的目录可能在老款 Kindle 上造成明显内存与设置膨胀。番茄官网公开页面可见至少 [4,909 章的长篇样本](https://fanqienovel.com/keyword/6209850)，因此本轮没有采用会误伤现有长书的低阈值，而是把单书上限设为 10,000 章、1,000 卷。连续数组检查会在遍历章节内容前拒绝已超限容器，跨卷时还会按总章节数再次门禁。自动测试覆盖恰好 10,000 章、10,001 章、6,000 + 4,001 跨卷累计和 1,001 卷；主刷新链路证明超限错误发生在 `Library.upsert()` 与设置保存前，旧书名和旧目录保持原对象不变，并明确提示书架、阅读进度和缓存未改变。该阈值是资源保护边界，不代表已验证所有超长作品；PW3 的真实 10,000 章解析耗时和峰值内存仍待专门测试。

## 2026-09-16 最近阅读的一键上下章

逐章 XHTML 由 KOReader 原生阅读器打开，旧体验要切换章节时必须离开正文、重新打开插件、进入书籍详情后再选择上下章。核对目标设备使用的 KOReader v2026.03 固定源码后确认，[`FileManager:openFile()`](https://github.com/koreader/koreader/blob/v2026.03/frontend/apps/filemanager/filemanager.lua#L1555-L1573) 会调用唯一受支持的 [`ReaderUI:showReader()`](https://github.com/koreader/koreader/blob/v2026.03/frontend/apps/reader/readerui.lua#L601-L631) 切换文档，并广播关闭现有 FileManager/ReaderUI；`after_open_callback` 只在新文档完成初始化后运行，不是阅读器关闭或返回旧菜单的回调。因此本轮没有虚构“返回后刷新旧详情页”，也没有依赖隐藏手势，而是在本地书架首页的最近阅读主操作后直接提供有效的下一章和上一章。用户在正文内从工具菜单重新打开 Fanqie Lite 后，一次点按即可切换；首章不显示上一章，末章不显示下一章。首页和详情页都显示目标章号，并把目标索引捕获在菜单渲染时，避免可变书籍状态让旧按钮指向与文字不同的章节。自动测试覆盖中间、首末边界、首页直达和渲染后状态变化；ReaderUI 内切换、返回路径、菜单残影和按键响应仍需 PW3 实机验证。

## 2026-09-14 离线可读目录与安全恢复

书籍详情过去只显示普通缓存文件数量，章节目录看不出具体哪一章能离线打开，也没有标出当前章节；断网用户只能逐章试错。缓存读取失败则一律被当成“缓存损坏”并发起联网，即使真实原因是缓存根或书籍目录超出安全范围，最终仍会在写入阶段失败。现在目录打开时会在既有真实路径和普通文件门禁后完整复验最多 12 个缓存，只对通过 XHTML 格式、控制字符、大小和完整结尾检查的章节标记 `[可离线]`，对安全范围内但损坏或不可读的文件标记 `[缓存需修复]`，并同时标出 `[当前]`。候选缓存超过插件约定上限、目录不可读或真实路径不可信时固定显示状态不可读，不扫描正文也不作离线承诺。实际打开时只有内容层损坏允许联网重建；缓存安全边界失败会在联网前停止，书架、进度和缓存均不改变。自动测试覆盖完整/损坏/未缓存目录、当前章节、异常数量零正文读取、错误脱敏及安全错误不联网；PW3 上目录打开耗时、长标题换行和标记辨识度仍待实机验证。

## 2026-09-14 首本书完整路径

首次使用流程过去虽然具备三个入口，但把不可用的扫码称为“实验性”，没有在列表上直接说明尚未开放；搜索/添加是当前默认可用路径，却没有推荐标识。更明显的语义冲突是：新书在首页显示“开始阅读”，进入详情后立刻变成“继续阅读”，安装指南也要求新用户寻找后者。现在保持产品规定的三个入口及顺序不变，同时将扫码标为“尚未开放”、搜索/添加标为“推荐”，并在输入框中优先引导官方链接、提示书名搜索可能遇到官网验证。首页和详情共用同一进度判断：只有本机打开记录或已验证的导入位置存在时才显示“继续阅读”，新书统一显示“开始阅读”。加入成功提示和五分钟指南也使用同一措辞；自动测试覆盖新书、本机进度和导入进度。真实五分钟耗时、PW3 换行与陌生新手理解仍需实机验证。

## 2026-09-14 解析失败三要素提示

书籍页、目录、搜索和章节解析过去直接把固定底层原因交给网络错误框，部分只说明“缺少字段”或“结构无效”，没有同时回答本地数据是否安全和用户下一步。现在这些调用点统一在写入之前通过同一消息边界补齐三段信息：失败的是哪一步、书架/阅读进度/缓存均未改变、以及对应的安全操作。书籍和目录建议核对官网页面与插件更新，搜索提示改用官方书籍链接，章节明确登录或解锁必须使用番茄官方客户端。合成测试覆盖书籍、搜索和章节调用链、固定回退、canary 不可见及 `__tostring` 不执行；目录复用同一函数，PW3 上长提示的分页和可读性仍需实测。

## 2026-09-14 目录接口失败状态拒绝

目录解析器过去只检查 `payload.data`，忽略顶层 `code`；官网若返回非零或畸形状态但仍携带残留章节数组，插件可能把失败响应保存为新目录。现在保持无状态码旧夹具兼容，并只接受数值 `0` 或字符串 `"0"` 的显式成功状态；其余状态在遍历章节前固定拒绝，提示本地目录未改变，不读取服务端 `message`，也不对对象状态调用 `__tostring`。失败测试先复现“非零状态 + 有效残留 data”被接受，再覆盖字符串零兼容、canary 不可见与对象状态。真实官网失败状态形态和 PW3 提示仍需矩阵验证。

## 2026-09-14 浏览器进度请求失败即停

浏览器导出器允许页面未产生可选阅读进度请求时生成无进度的最小书架；但旧实现也会把已经发出、却返回非零状态或畸形结构的进度响应静默当成空数组，导致登录失效或官网错误被伪装成成功下载。现在两种情况严格分离：未发现请求仍可导出，已发现请求则必须返回成功数组，否则在创建 Blob 和点击下载前使用固定错误停止。合成测试覆盖非零状态中的凭证 canary 不可见、未知结构拒绝、未发现请求兼容及完整运行路径不产生残缺下载。真实失效登录响应形态仍未用账号验证，本次没有访问浏览器会话或账号。

## 2026-09-14 浏览器先导证据与安全操作说明

2026-09-08 已用专用测试账号的两本未读书完成一次真实浏览器导出，但 README、质量计划和格式文档仍停留在“尚未验证、以后补步骤”的旧状态，导致候选证据自相矛盾。现在统一记录这项有限通过，并明确不扩张为作者、已读进度、分组、多页、大书架或失效登录已验证；格式文档补充按候选提交核对脚本、使用 Chrome Snippets、固定失败停止、USB 导入、合并语义和中转文件隐私的逐步说明。候选包同时纳入浏览器先导验收原文，自动测试锁定关键安全警告和证据文件清单。此修改不运行脚本、不访问账号，也不把开发工具升级为普通用户成熟功能。

## 2026-09-13 打开成功后再消费导入位置

浏览器 JSON 导入的章节内位置最初在 `FileManager.openFile()` 前就从设置候选中移除并保存；若阅读器初始化异常，用户虽未进入正文，重试时却已失去原始导入位置。本轮先改为两阶段提交：准备打开时只检查并保留位置，在 `openFile()` 同步调用返回后再消费和安全保存。同步打开异常时位置会保留，清理写入失败也会由现有事务恢复打开前状态；普通本地书籍仍只写一次设置。后续固定源码审计证明 `openFile()` 返回只代表异步打开已排队，仍不能证明文档初始化成功；2026-09-20 已进一步改为等待 `ReaderReady`，详见本日志顶部记录。

## 2026-09-13 章节文件打开异常边界

章节状态保存后，缓存与联网路径最终都会调用 `FileManager.openFile()`；该同步调用及当时安装的导入百分比回调原本没有本地错误边界。这里加入的 `pcall` 只拦截排队阶段同步抛出的异常，提示不会回显对象，并明确书架和缓存未删除、但此前安全保存的继续阅读位置可能已更新到本章。后续固定源码审计确认真正的文档加载位于 `nextTick` 协程，不能由这层 `pcall` 覆盖；2026-09-20 已将位置应用与消费移到 `ReaderReady` 回调。真实异步损坏 XHTML 的最终 KOReader 行为仍需实测。

## 2026-09-13 本机阅读位置检测失败边界

插件打开缓存或新下载章节前会调用 KOReader `DocSettings:hasSidecarFile()`，用于避免浏览器导入的百分比覆盖已有 `.sdr` 本机位置。该调用原本位于可取消网络任务之外；文件系统或 DocSettings 异常会直接越过插件边界，离线打开也可能退回文件管理器。现在先以 `pcall` 检测 sidecar，失败时停止打开并使用固定中文提示，既不回显底层异常，也不消费导入位置、更新当前章节或写设置。合成 canary 先复现异常逃逸，再验证状态调用次数为零及正常 sidecar 生命周期不变；仍需真机验证实际损坏或不可读 `.sdr`。

## 2026-09-13 刷新目录后重建书籍页

无目录书籍首次联网获取成功后会重新打开详情页，但已有目录的“刷新书籍信息与目录”只更新内存和设置，当前菜单仍保留刷新前的标题、章数、继续阅读位置及上下章入口，用户必须手动退出再进入。两条路径现在对称：刷新成功保存后，在下一次 UI tick 重新按书籍 ID 构建详情；刷新失败抛出前不会安排重建，仍由既有错误边界说明数据状态。契约测试先复现“成功刷新后未重新打开”的旧行为，再锁定刷新与同书页面重建。该测试不替代 PW3 上目录增加/减少后的分页、残影和返回体验验证。

## 2026-09-13 兼容性矩阵绑定完整提交

候选包的 `BUILD-INFO.txt` 已保存完整 40 位 Git 提交，但 v2 兼容性记录仍允许 7 位短哈希。短哈希可能随仓库增长变得歧义，不能长期证明 30 本/90 场景测试的是哪一份代码。证据验证器现在只接受 40 位小写十六进制提交，采集文档要求该值与候选包元数据完全一致；短哈希和混合提交测试分别锁定格式与单一候选约束。该修改增强可追溯性，工具本身仍不能证明记录来自所声明提交，也不增加真实矩阵数量。

## 2026-09-13 固定取样序号进入证据门禁

兼容性取样器一直会计算目录前部、第 `floor((N + 1) / 2)` 章和末章的真实序号，但证据记录只保存人为填写的 `first/middle/latest` 标签与章节 ID；原门禁因此无法证明三条记录确实来自固定位置。开发用记录格式升为 v2，新增必填 `chapter.ordinal`，并在统计前校验前部为 1、中部为规定中点、末尾等于目录章数。v1 固定拒绝；仓库没有依赖它的正式证据文件，已有先导本来也不计入发布门禁。合成完整矩阵和错误序号测试已锁定这一规则，但真实采集器仍须把取样计划中的序号原样传入，30 本/90 场景数量没有增加。

## 2026-09-13 兼容性证据 ID 边界统一

生产解析、书架、缓存和导入已经统一接受 10–64 位数字书籍/章节 ID，但兼容性证据工具仍沿用 10–30 位限制；未来若遇到 31–64 位合法 ID，正式矩阵会在记录阶段产生假失败。证据工具现在复用同一数值边界，测试锁定 64 位书籍与章节 ID 可记录、65 位固定拒绝。此修改只修正证据格式一致性，不增加 30 本/90 场景的已通过数量，也不代表已经观察到官网使用 30 位以上 ID。

## 2026-09-10 五分钟安装的联网前置条件

候选安装指南过去到最后才说明首次章节需要联网，用户可能完成复制后才发现飞行模式或错误设备时间阻断取目录，形成虚假的“5 分钟失败”。指南现在把可信 Wi-Fi、关闭飞行模式和基本正确的 Kindle 时间列为首次阅读前置条件，在进入插件前再次核对，并明确离线只能验证插件加载、不能计作五分钟阅读通过；网络恢复后无需重装。候选包测试锁定这些说明和当前“开始阅读（第 1 章）”成功路径；真实连接耗时、系统网络确认和陌生新手计时仍须实机验证。

## 2026-09-10 隐藏不可用的相邻章节操作

书籍详情过去在第一章和最后一章仍显示不可执行的“上一章”或“下一章”，点击后才报告目录边界。现在只在目标章节确实存在时显示相邻章节入口：中间章节保留两项，第一章只显示下一章，最后一章只显示上一章，单章书不显示两项；`open_chapter()`原有边界校验继续保留，用于防御陈旧回调或状态变化。契约测试覆盖前、中、末位置；真机菜单分页、位置稳定性和用户理解仍待验证。

## 2026-09-10 书籍详情阅读主操作

书籍详情过去先显示一段不可操作的本地状态，把“继续阅读”或“联网获取目录并开始阅读”放在第二项。现在详情页先给出与书籍状态匹配的唯一主操作，本地目录、缓存和离线说明紧随其后；章节目录、上下章、刷新、清缓存与移除的相对次序不变。独立契约测试覆盖有目录与待获取目录两种详情、主操作回调及后续管理入口；该顺序仍需在 PW3 验证长标题、状态换行、首项触摸和返回体验。

## 2026-09-10 首页阅读主操作

交互审计发现，非空书架仍把扫码、添加和文件导入固定放在最前，继续阅读必须先进入书籍页，不符合“继续阅读优先”。首页现在独立按最近阅读选择主书，不受用户当前书架排序影响：有本机或导入进度时显示“继续阅读”，有目录但尚未开始时显示“开始阅读”，尚无目录时只打开书籍详情，不越过联网确认。书籍列表后仍保留添加、文件导入和实验性扫码的可见入口；空书架的三个首次使用入口及顺序不变。契约测试覆盖主操作文字、直接打开章节、书名排序与最近阅读分离、待目录安全回退和全部可见入口；PW3 上的换行、触摸、残影和返回体验仍待验证。

## 2026-09-10 独立定位与交互参考

项目继续独立开发，不并入或依赖 Moon、Bookshelf 等综合插件，也不追逐与番茄阅读无关的功能数量。外部项目只用于校准信息层级与墨水屏操作：继续阅读优先、关键入口可见、长按承载低频操作、手势必须有按钮或菜单兜底、危险操作保持分离。上述原则已写入 P1 与发布候选门禁；自动入口测试仍不能替代 PW3 性能、残影、触摸手感和陌生新手理解验证。

## 2026-09-10 作者字段最小诊断

首次真实浏览器导出的两本书没有作者，现有证据不能区分“详情响应没有作者”和“导出器字段映射错误”。开发工具新增显式布尔开关控制的作者字段诊断模式：仍只访问既有官方书架与详情只读请求，不请求阅读进度、不下载文件、不枚举未知字段，也不显示任何字段值；报告只包含六个预先列出的候选字段及其 `string`、`null`、`array`、其他基础类型或缺失次数。合成 canary 证明作者值、嵌套 Token 和未知敏感键不会进入报告，诊断路径只发起两次请求。该模式尚未在真实测试账号运行，不能据此声称作者字段已经修复。

## 2026-09-07 浏览器导出请求边界

真实测试账号导出前发现浏览器 fetch 默认跟随重定向，且响应流没有请求期限。导出器现强制 `redirect: error`，每次请求使用 20 秒 AbortController 期限，覆盖等待响应头和读取正文；结束时取消计时器并中止剩余传输。合成测试覆盖两阶段超时、重定向选项覆盖和三请求完成后的清理，不回显底层错误。尚未证明真实账号导出成功；后台浏览器计时器节流可能延后取消，不宣称严格墙钟上限。

12000 层合成设置复现了递归敏感字段扫描的栈溢出。复制、扫描和相等比较现使用显式工作栈，保留循环和共享引用的原有处理，不按深度截断数据。测试覆盖深层凭证、复制、相等及深层叶值变化，并验证自引用和共享对象复制。此修改只消除这三个遍历操作的调用栈限制；LuaSettings 加载、dump 序列化及总内存消耗仍须单独验证，不能视为任意损坏设置恢复完成。

## 起点

这个项目源于一个很直接的问题：已经能在 Kindle Paperwhite 3 上运行 KOReader，能否也用它阅读番茄小说？

第一步不是编写界面，而是确认技术边界。调研发现，番茄小说的官方阅读网页包含服务端渲染的章节状态；目录也可以由官方网页接口取得。但此前看到的非官方实现会依赖第三方聚合正文源，这不符合本项目希望保持的范围。

因此，0.1.0 确立了几条原则：

- 只请求 `fanqienovel.com` 官方网页。
- 不登录，不接触账号 Cookie 或个人书架。
- 不批量下载整本书。
- 不绕过付费、登录或章节锁定。
- 无法可靠解析时明确失败，不把乱码写入缓存。

## 第一个原型

原型验证了三件关键事情：

1. 书籍页面可以提取书名和书籍 ID。
2. 官方目录响应可以整理成 KOReader 可操作的章节列表。
3. 公开章节中的 PUA 字符可按当前映射还原成正常文字。

插件采用很小的分层：`http.lua` 负责受限的网络请求，`parser.lua` 负责页面和章节解析，`pua.lua` 负责字符映射，`storage.lua` 只管理插件自己的缓存，`main.lua` 连接 KOReader 菜单和阅读器。

## 第一次完整自检

在准备 0.1.0 时，自检发现并修复了三个会影响真实使用的问题：

- 中文长度最初按 UTF-8 字节数统计，可能误判短预览；现改为按 Unicode 字符计数。
- 目录定位最初调用了 KOReader 中不存在的方法；现使用 2026.03 实际提供的分页接口。
- 网络底层抛出异常时可能无法恢复全局超时；当时已保证 HTTP 请求异常后仍会调用复位。后续审计发现设置/复位函数自身的异常仍未覆盖，2026-09-20 已增加独立边界，详见本日志顶部记录。

最终验证覆盖 Lua 5.1 语法、核心离线测试、官方书籍页、目录、公开章节和登录墙页面。桌面端验证通过后生成了第一个安装包。

## 第一次 Kindle 实机验证

2026-08-16，0.1.0 被复制到 Kindle Paperwhite 3（固件 5.16.2.1.1）上的 KOReader 2026.03。KOReader 正常启动，工具菜单出现“番茄小说（实验版）”，离线说明页面可以打开。连接 Wi-Fi 后，测试书籍的书名与当时最新的 88 章目录正常显示；打开第一章后，正文完整、无乱码，KOReader 翻页正常。

这次结果把项目状态从“桌面端可行性验证”推进到了“单台 PW3 实机验证通过”。它仍不是对所有 Kindle 型号、KOReader 版本或未来网页结构的兼容性保证。

## 多书本地书架

稳定版候选的第一项改造从本地数据开始，而不是先做账号登录。原因是登录属于可选能力，不能成为日常阅读体验的前提。

新书架以带版本号的数据结构保存多本书，每本书独立记录目录、最后阅读章节、添加时间、目录更新时间和最近打开时间。首次启动新版时，0.1.0 的单书设置会自动迁移；同时保留并同步旧字段，使用户仍可降级回 0.1.0。刷新目录时优先按章节 ID 找回原阅读章节，避免目录前方新增章节后进度错位。

删除边界被刻意拆成两个动作：“从书架移除”不删除缓存，“清理缓存”不删除书籍和进度，且都需要用户确认。缓存清理只接受数字书籍 ID，并只删除插件目录内符合数字章节名规则的 XHTML 与临时文件。

## 网络边界审计

审计发现原型虽然设置了 20 秒总超时，但自定义响应接收器没有实际检查总耗时；慢速分块响应可能持续阻塞界面。修复后，接收器同时检查累计时间和 1 MB 大小限制，并在请求成功、失败或 HTTP 底层异常后调用 KOReader 的全局网络超时复位。2026-09-20 又补上设置/复位函数自身的异常边界；复位失败时只能停止并要求重启，不能声称全局状态已经恢复。

网络模块现在只接受 `https://fanqienovel.com/` 地址，明确禁用重定向，并检查声明的响应长度。超时、证书、重定向、权限、限流、页面不存在和服务端错误会转换成可操作的中文提示，同时说明本地数据没有改变。

## 安全 JSON 导入

浏览器文件导入先实现 Kindle 端的严格接收边界。插件只显示并接受名为 `fanqielite-bookshelf.json` 的文件，读取前限制为 256 KB，解析后要求固定格式版本、连续书籍数组、最多 500 本、字符串 ID、字段长度和 0 到 1 的阅读位置。

导入采用字段白名单，并递归拒绝 Cookie、Token、session、CSRF、密码、手机号和授权头等凭证字段。全部书籍通过验证后才显示新增与更新数量；用户再次确认后才写入本地书架。导入已有书籍时保留其目录、缓存和本地阅读进度；新书首次打开时再从番茄官方地址获取目录。

文件读取边界的后续审计发现，`io.open` 的原始系统错误会进入界面，文件定位、读取或关闭抛异常时还可能越过“现有书架没有改变”的失败说明。现在打开、末尾定位、大小验证、回到开头、完整读取和关闭均使用 `pcall` 与固定中文分类；只有读取字节数与预先确认大小一致且文件安全关闭后才进入 JSON 解码。合成 canary 覆盖打开、大小定位、回到开头、读取、关闭和主界面非字符串错误，修复后不显示 canary 且不调用 `__tostring`。该证据不替代 Kindle 上误选、拔线、只读或损坏文件的集中真机验证。

## 搜索功能的失败实验

2026-08-16 检查了番茄官网当前使用的 `/api/author/search/search_book/v1`。未登录的直接只读请求返回 HTTP 200 但正文为空；在官方搜索页执行相同关键词时，页面出现滑块验证，结果保持为空。

这意味着“在 Kindle 中直接按书名搜索”目前没有经过验证的稳定官方路径。项目不会绕过验证码，也不会为了填补入口而接入第三方搜索源。界面应继续诚实说明当前只支持官方链接或 ID；搜索只有在找到合法、稳定且可在 Kindle 上完成的官方流程后再实现。

## 缓存完整性边界

章节缓存不能只凭文件存在就交给 KOReader 打开。插件现在会先检查大小、固定 XHTML 结构、完整结尾和 XML 非法控制字符；损坏缓存会被拒绝，并在不改变书架与阅读进度的前提下尝试联网重新获取。

写入仍采用同目录临时文件和原子改名，同时开始检查 `write` 与 `close` 两个阶段。磁盘写满、只读或关闭文件失败时会删除未完成的临时文件，保留原有正式缓存，并提示用户检查空间或只读状态。

后续错误边界审计发现，缓存创建、写入、关闭、改名、读取、目录遍历和删除仍可能把底层系统错误拼入用户提示，异常对象还可能触发 `__tostring`。现在这些操作都封装在 `pcall` 或不读取异常内容的 best-effort 清理中，只返回固定中文阶段或经程序统计的成功/失败数量。创建、写入、关闭或改名失败会清理 `.tmp`；读取失败不会把损坏或不可确认的文件交给 KOReader；清理仍只接受数字书籍 ID，并只删除 `数字.xhtml` 与 `数字.xhtml.tmp`，不会删除同目录其他文件。

合成 canary 覆盖属性读取、目录打开与迭代、缓存创建/写入/关闭/改名、章节读取、自动淘汰、手动部分清理和主界面非字符串错误。修复前原始异常会传播或出现在提示中；修复后 canary 不可见且 `__tostring` 调用次数为零。

缓存持久性随后复用 KOReader 的 `fsyncOpenedFile()`：临时正文完整写入后先同步文件，关闭后重新读取并执行同一套 XHTML 大小、结构、控制字符和完整结尾校验，只有通过才原子替换正式缓存。同步、关闭或复验失败都清理 `.tmp` 并保留原正式文件；替换后调用 `fsyncDirectory()`，但与设置写入相同，目录同步发生在替换之后，只能作为 best-effort。故障注入覆盖同步异常、重读截断和目录同步异常，不把异常对象送入提示。这里仍不声称已通过断电级验收，也未在只读或满盘的 Kindle 文件系统上完成集中验证。

## 设置写入完整性

核对 [KOReader 2026.03 的 `LuaSettings`](https://github.com/koreader/koreader/blob/v2026.03/frontend/luasettings.lua) 与 [`util.writeToFile()`](https://github.com/koreader/koreader/blob/v2026.03/frontend/util.lua#L1141) 后确认，`LuaSettings:flush()` 不会把底层写入失败返回给调用方，而底层也未检查 `write()` 和 `close()` 的结果。插件不能用 `flush()` 的返回值证明书架或进度已经落盘。

因此插件设置改为先生成临时 Lua 设置文件，调用 KOReader 的 `fsyncOpenedFile()`、关闭并重读校验后，再原子替换正式文件；每次替换前用同样流程保存上一版 `.old`。改名前的写入、同步、关闭、临时重读校验或改名失败会保留主设置，本次内存修改回滚，界面说明检查空间/只读状态。2026-09-20 的后续审计补上替换后的最终重读：失败时自动恢复上一版，恢复也失败则报告磁盘状态无法确认，详见本日志顶部记录。网络操作的用户提示也不再展示 Lua 调用栈。

后续错误边界审计发现，上述步骤虽然能阻止失败文件替换正式设置，但 `io.open`、`write`、`fsync`、`close` 和 `os.rename` 的底层错误仍会被 `tostring()` 后送往界面；序列化器返回非字符串对象时，拼接设置文本也会触发元方法。现在创建和改名也置于 `pcall` 内，序列化结果必须是字符串，各失败阶段只返回固定分类，临时文件清理采用不读取异常的 best-effort。主界面只接受字符串设置错误，否则使用固定“没有返回可安全显示的错误说明”，再恢复上一版内存状态。

合成 canary 覆盖序列化对象、创建抛错、同步/关闭异常对象、改名抛错和主界面异常返回；修复前测试会显示 canary 或调用 `__tostring`，修复后调用次数为零，正式设置逐项保持旧值且无 `.tmp` 残留。这里仍不声称已经解决断电窗口：正式文件内容在改名前已 fsync 并复验，但目录 fsync 发生在替换后且只是 best-effort，仍需在目标 Kindle 文件系统上单独验证。

## 真正可取消的网络任务

KOReader 2026.03 官方的 [`Trapper:dismissableRunInSubprocess()`](https://github.com/koreader/koreader/blob/v2026.03/frontend/ui/trapper.lua) 会让 UI 保持响应，并在用户点按取消时终止和回收子进程。插件只把无副作用的官方 HTTP GET 放进子进程；解析、书架修改、缓存写入和设置保存仍留在主进程，并且只在完整响应返回后发生。

因此取消书籍信息、目录或章节请求时，不会留下临时下载、半份响应或内存里的书架修改。并发点击会被“已有网络操作”门禁拒绝。该机制仍需在 PW3 上验证点按响应、强制退出和 Wi-Fi 切换。

## 解析安全变体

章节与书籍 ID 现在统一要求至少 10 位数字，并拒绝响应 ID 与请求不一致。锁定判断同时覆盖布尔 `true`、数字 `1` 和字符串 `"1"`/`"true"`，避免接口序列化方式变化后把受限章节误当成公开正文。

PUA 解码前的 UTF-8 扫描补齐了续字节、过长编码、代理区和超过 U+10FFFF 的边界。无效 UTF-8 与未知 PUA 都会在生成缓存前安全拒绝；合法四字节字符保持不变。自动测试同时覆盖畸形目录、书籍/章节 ID 不一致、数字和字符串锁定标志。

## 缓存清理的部分失败

清理缓存过去只统计删除成功的文件，删除失败会被静默忽略，界面仍可能显示“已清理”。现在目录打开/遍历错误会直接失败；若只删除了部分文件，插件会分别报告成功数、失败数和首个系统错误，并明确未删除缓存仍可使用、书架和进度没有改变。

删除白名单仍只允许数字章节名的 `.xhtml` 与 `.xhtml.tmp`。目录里即使出现未知文件也不会删除；因此未知文件导致空目录移除失败时不会把它当成缓存清理失败。

## 本地书架安全导出与数据设置

插件现在可把本地书架导出为与严格导入器相同的版本 1 JSON。生成内容只使用书籍白名单字段，并在写入前通过导入验证；同目录临时文件完成写入和同步后会再次解析验证，随后原子替换固定文件名并做最终复验。失败不会改动书架、缓存或插件设置，也不会把部分写入报告成成功。

文件系统错误边界的后续审计发现，导出创建、写入、同步、关闭、重读、校验和改名仍会把底层错误拼入用户提示，`io.open`、读取或 `os.rename` 抛异常时还可能越过导出失败说明。现在这些阶段都使用 `pcall` 与固定中文分类，临时文件删除为不读取异常的 best-effort；主界面也只接受字符串错误，否则显示固定安全回退。合成 canary 覆盖创建、写入、同步、关闭、清理、重读、改名和非字符串 UI 错误，修复后不显示 canary 且不调用其 `__tostring`。这不替代只读、满盘或断电真机验证，也不改变导出文件位于 Kindle 用户盘根目录、可被 USB 读取的隐私边界。

导出当前章节时只使用插件确实记录的章节 ID 与标题，不虚构章节内百分比；从已验证文件导入且尚未加载本地目录的合法百分比可以原样迁移。“设置与数据”同时集中显示导入/导出、缓存与隐私边界，以及仅供用户手动执行的完整卸载路径，插件本身不执行自动删除。

## 官方浏览器验证挑战

2026-08-17 对番茄官网当前公开搜索流程的只读审计确认：网页使用 `/api/author/search/search_book/v1`，但匿名直连可能返回 HTTP 200、空正文和 `Bdturing-Verify` 滑块验证响应头。使用插件现有浏览器 User-Agent 仍会触发；搜索页本身也不服务端输出结果。Kindle 无法可靠完成该网页滑块，因此插件不会尝试绕过或复用验证令牌，书名搜索暂不能据此宣称稳定可用。

网络层现在会识别官方验证响应头而不记录或展示其值，明确提示“官方安全验证、Kindle 无法显示、稍后重试或粘贴官网链接”；其他无挑战头的空响应也会安全拒绝。两种情况都不会进入解析、缓存或书架写入阶段。

在此边界上，书名/作者搜索采用有限的“尽力而为”模式：只访问上述番茄官方 HTTPS 接口，只请求第一页 10 条结果，并严格验证连续数组、数量、字符串书籍 ID、标题和作者字段。无效条目不会进入书架；选中结果后仍复用既有书籍页与目录验证流程。官网正常返回时新手可直接搜索加入，出现滑块挑战时则明确回退到粘贴官网链接，不能把该能力描述成所有网络下都可用。

搜索响应状态码的后续审计发现，直接 `tonumber()` 会把 NaN、无穷、小数和科学记数法字符串当成可显示的服务代码，响应字段变为对象时不同 Lua 实现的行为也不应被信任。现在只接受 32 位有符号整数或最多 11 位的十进制整数字符串；其余类型统一显示固定“官方搜索暂时不可用”。合成测试覆盖对象 canary、NaN、正负无穷、小数和科学记数法，均不回显原值或调用 `__tostring`。

## 兼容矩阵完成门禁

现有兼容证据工具原本只统计记录数和正确率，即使样本全来自同一长度档、每本只测一个位置或完全没有安全拒绝场景，也可能给出看似良好的摘要。现在普通模式仍允许查看部分采集进度，`--require-complete` 则强制验证不少于 30 本/90 场景、五档 5/5/8/7/5 配额、至少 12 本完结与 18 本连载、每本互不重复的前中末三处、同一插件候选提交、男频/女频及出版或版权受限覆盖、公开正文至少 95% 正确，以及短预览、登录墙、锁定、畸形响应、章节 ID 不一致和未知 PUA 各至少一个安全拒绝场景。

所有非公开或未知 PUA 场景只有在结果为安全拒绝、未写缓存、未显示乱码且给出可操作提示时才算通过。新书/较早作品和结构哈希来源无法从匿名白名单字段自动证明，继续保留人工复核；限流也不得为满足类型而主动触发。自动门禁只证明证据文件满足口径，真实 30 本/90 场景尚未采集，不能提前宣称兼容率达标。

## 目录时间与离线状态

书籍页现在只用本地数据展示目录章数、缓存文件数和目录上次成功刷新时间，并明确说明离线只能打开完整缓存。缓存数量仍按文件统计，不会被表述成“保证可读章节数”；缓存目录无法读取时也会直接显示状态不可读。

新增的 `directory_updated_at` 只在成功获取并写入目录时更新。旧书架和仅通过 JSON 导入、尚未联网取目录的书不会拿元数据更新时间冒充目录时间，而是显示“下次联网刷新后记录”；时间戳明显超过设备当前时间时提示先校准设备。自动测试覆盖首次目录、再次刷新、导入不覆盖、旧数据、缓存不可读和未来时间戳，真机界面布局暂缓验证。

## 去正文解析夹具与实体边界

原有解析测试把状态表直接写在单个测试文件中，难以持续扩展，也没有证明卷目录、平铺目录、ID 目录和安全拒绝场景使用同一套稳定口径。首批独立夹具现在只使用虚构 ID 与重复生成的合成文字，不保存真实书名、作者或完整正文；逐项记录预期通过结果或必须出现的可操作拒绝原因。

新增失败夹具发现两个会破坏安全失败原则的缺口：目录列表混入非法章节或重复 ID 时，解析器过去会静默保留部分结果；未知 PUA 或非法 Unicode 通过数字 HTML 实体表示时，可以绕过实体解码前的字符检查。现在选中的目录结构只要包含无效条目、重复 ID 或错误容器类型就整体拒绝，避免用截断目录覆盖本地状态；十进制和十六进制实体先按 XML 合法字符范围验证，实体解码后再次检查 UTF-8 与 PUA。合法实体及已知 PUA 仍可正常解码，完整测试通过。真实网页矩阵尚未采集，因此不能把夹具通过解释为兼容率已经达标。

字段类型审计随后发现，书籍/章节 ID、标题、作者、目录序号、正文字数和正文曾使用隐式 `tostring()` 或 `tonumber()`；更严重的是，`needPay` 或 `isChapterLock` 变成对象时会被当作 false，可能把未知权限状态误判为公开。现在 ID 只接受数字字符串，存在的文本与正文只接受字符串，序号和字数只接受有限非负整数，权限只接受 nil/false/0/`"0"`/`"false"` 与 true/1/`"1"`/`"true"`。未知权限、对象正文或畸形字数都会在 PUA 解码和 XHTML 生成前拒绝。合成 canary 证明对象书名与正文不会触发 `__tostring`；这些夹具仍不能替代真实网页结构矩阵。

用户可见文本边界继续与本地导入格式对齐：书名和章节标题最多 300 字节，作者最多 150 字节，并在去除首尾空白前拒绝 NUL、换行、制表和其他控制字符，避免网页字段伪造多行菜单或膨胀设置。正文单独限制为 1 MB，允许 XML 合法的 Tab、LF 和 CR，拒绝 NUL、DEL 及其他 C0 控制字节；非法正文会在 PUA 和 HTML 处理前停止。夹具覆盖超长标题、作者换行、目录标题换行、正文 NUL、正文超限及合法正文空白，不能替代真实长章节兼容验证。

目录容器审计还发现，Lua `ipairs` 会在第一个空洞停止并忽略字符串键，因此稀疏卷列表、稀疏卷内章节或混入额外键的 ID 列表可能被截断后错误接受。现在被选中的外层卷、直接卷数组、卷内 `chapterList`、平铺 `chapterList` 和 `allItemIds` 都必须只含从 1 开始的连续整数键；合法卷对象在其 `chapterList` 之外的元数据不受影响。夹具证明任一空洞或混合键都会整体拒绝，不会返回部分目录供 `Library.upsert()` 覆盖本地状态。

正文清理过去只移除全小写 `<script>` 与 `<style>`，混合大小写块会在通用去标签后留下内部文本。足够长的脚本或样式文本因此可能让实际只有几个字的预览页越过 500 字门槛。现在完整块以大小写无关、标签名 frontier 边界明确的规则移除，避免误匹配 `<scripture>` 等名称；清理后仍残留的 script/style 开闭标签视为未闭合异常并整体拒绝。合成夹具覆盖带属性的混合大小写脚本、多行样式和未闭合脚本，均不能贡献可见正文长度。

同一长度门禁无法模拟浏览器 CSS：`hidden`、`aria-hidden="true"`、`display:none` 或 `visibility:hidden` 容器中的长文本过去也会在去标签后被计算为可见正文。插件现在逐个检查标签的小写副本，只有明确隐藏属性或声明才整体拒绝，不尝试猜测嵌套布局；普通正文单词 hidden、`class="not-hidden"`、`display:inline` 和 `visibility:visible` 不受影响。四类隐藏夹具均在长度统计和缓存前停止，但 CSS class、外部样式表和复杂渲染仍只能在真实矩阵中识别。

HTML 注释同样不可见，但通用 `<[^>]+>` 模式会在注释正文内部第一个 `>` 提前结束，剩余长文本过去可参与长度统计。现在标准 `<!-- … -->` 注释在其他标签处理前完整移除；清理后残留任一开始或结束边界都作为未闭合/畸形注释拒绝。夹具覆盖包含 `>` 的长注释、未闭合注释和经 `&lt;`/`&gt;` 转义后应当可见的注释文字，后者在实体解码后仍正常显示。

同一个通用去标签模式还会把引号属性中的合法 `>` 当成标签终点：长属性尾部可能泄露成正文并凑够公开长度，位于该字符之后的真实 `hidden` 属性也不会进入旧的标签检查。正文清理现在逐字节寻找引号之外的结束符，再解析实际属性名和值；标签属性整体移除，真实隐藏属性仍安全拒绝，而普通 `title` 值中的 hidden 单词保持兼容。夹具分别证明长属性不能满足正文长度、引号后的隐藏属性会被识别，以及长公开正文不会夹带属性尾部。

开始真实兼容采集前复核证据口径时发现，旧工具把任意 `result=success` 且“无乱码”的公开响应计为正确，即使同条记录明确写着缓存未保存、可见正文不足 500 字、只达到官方声称字数的一小部分或仍含未知 PUA。95% 门禁因此可能高估实际可读性。公开正确记录现在必须同时满足解析器的两条可见长度门槛、未知 PUA 为零且缓存已经保存；四类单记录夹具和一组低于 95% 的完整矩阵夹具锁定了该口径。该检查只能验证记录内部一致性，仍不能替代采集过程与原始公开页面的人工核对。

矩阵规范原先要求结构哈希不可来自完整正文，却没有标准生成方法。新的 `--fingerprint` 离线模式从标准输入读取最多 2 MB 的 JSON，只将排序后的字段名、值类型及数组中不同的元素结构组成规范模型再计算 SHA-256；字符串内容、数字/布尔值和数组长度不会进入模型。测试证明完全不同的正文、ID 和真假值在字段结构相同时得到同一指纹，新增字段会改变指纹，畸形输入不会回显 canary；深度和节点数也有固定上限。工具仍无法证明记录填写者实际使用了该模式，真实证据入库前必须人工复核来源并删除私有原始响应。

首次使用流程审计确认首页已经按产品顺序提供扫码、搜索/添加和文件导入三个入口，但未开放的扫码入口过去只显示泛化“开发中”，没有告诉新用户账号是否被请求，也没有指出可立即使用的替代路径。现在该提示明确说明当前版本未发起账号授权、未请求或保存登录信息、已有本地书架不受影响，并列出搜索/添加与文件导入。新的首页契约测试同时锁定标题、三个入口顺序和回调连接；实际文字布局、触摸体验与 5 分钟完成时间仍须陌生新手真机验证。

候选安装指南的升级步骤过去只要求复制旧 `fanqielite.koplugin`，但书架设置、章节缓存和 KOReader `.sdr` 阅读位置都位于插件目录之外；新版迁移设置后，仅恢复旧代码并不能证明已回到同一状态。指南现在要求升级前把插件、当前/上一版设置、整个插件数据目录和可选导出 JSON 复制到同一个带日期的电脑备份。回退先尝试只恢复代码；只有旧版无法读取当前状态或用户明确需要完整还原时，才从同一快照一起恢复设置与数据，并警告会丢弃快照后的变化。候选包测试锁定三个运行路径和“同一份升级前备份”说明，但真实升级/降级演练仍未因此完成。

## 自动缓存淘汰失败提示

章节成功原子写入后，插件会把每本书的缓存限制在 12 个，但旧实现忽略了自动淘汰的目录遍历和删除结果。只读文件或目录错误因此可能让缓存数量持续增长，界面却没有任何提示。测试还证明，当设备时间异常使新文件时间戳看起来更旧时，单纯按修改时间排序可能误删刚写好的当前章节。

现在淘汰器会显式保护本次写入的章节，时间相同时使用稳定路径顺序，并分别统计成功数和失败数，不再显示底层系统错误。新章节已经完整写入时不会因旧缓存删不掉而被丢弃或阻止阅读；阅读器打开后会说明“章节已保存”、书架与当前章节未损坏，并建议稍后手动清理或检查空间与只读状态。缓存说明也改为“最多 12 个、优先清理较早写入”，不再错误声称按最近打开顺序淘汰。自动测试覆盖目录不可读、全部删除失败、异常时间戳保护和警告透传；真机布局及只读/满盘行为仍待集中验证。

## 候选测试包与 5 分钟安装路径

直接下载 GitHub 源码压缩包会额外套一层带分支名的目录，新手若原样复制，KOReader 无法在预期路径找到 `_meta.lua`。仓库过去也只有一句安装说明，没有验证包内是否混入测试、工具、设置或缓存，更没有升级备份、失败判断和安全回退步骤。

新的候选包构建只复制明确白名单：运行 Lua、许可证、README、安装指南、变更记录，以及 README 直接引用的书架格式、兼容矩阵、质量计划和安全审计文档，避免包内说明出现断链。生成结果固定为单层 `fanqielite.koplugin/`，不超过 1 MB，文件名和 `BUILD-INFO.txt` 绑定 Git 提交，并配套 SHA-256；默认拒绝从未提交工作区生成候选包。自动测试会核对每一个包内路径、提交身份，解压后再次检查 Lua 5.1 语法，同时拒绝任何意外文件。中文指南按 0–1、1–3、3–4、4–5 分钟拆分目录检查、复制、安全弹出、重启和加入第一本书，并提供升级备份、官网验证、TLS、预览/锁定、回退和卸载说明。脚本只在本地或 CI 生成测试产物，不创建 Release、不上传、不打标签；真正的 5 分钟门禁仍须陌生新手实测。

## 扫码威胁模型与设置硬门禁

真实扫码实现前先完成独立威胁模型，明确 QR 载荷、轮询票据、Cookie、CSRF、Token、授权头和退出票据都是瞬时凭证；本地只允许保存最小书架数据。模型不声称 Lua 字符串可以可靠清零，也不把官方退出成功当作本地安全前提。它要求在显示最终导入确认前完成退出尝试并清除凭证引用，同时把二维码真机行为、HTTP/Cookie 子任务、当前官方授权主体、会话有效期和退出语义列为重新验证前的 No-Go 条件。

自动失败测试同时发现，虽然当前 `state_table()`不会投影插件根部的瞬时会话、`Library.import_books()`也只复制书籍白名单字段，但底层 `Persistence.write()`过去仍会忠实写入调用方误传的嵌套会话字段。现在候选状态和上一版备份在任何文件创建前都会递归拒绝账号、二维码、票据、Cookie、CSRF、Token、请求头等字段；错误只返回固定分类，不回显字段值。普通书名中出现 Cookie/Token 文字不会误拒绝。合成 canary 测试覆盖状态投影、现有/新书导入、主设置和 `.old` 拒绝；真实账号、Passport 请求和二维码仍完全未接触。

## 端点无关的一次性会话核心

在确认真实 Passport 协议前，先把不依赖接口的生命周期做成独立纯 Lua 模块。模块不接 UI、HTTP 或本地书架，只负责单实例运行代号、五分钟总时限、二维码过期、授权后取数、退出尝试、待确认数据和提交结果；任何迟到的旧运行结果都会被当前运行代号拒绝。待确认书架必须再次经过现有 JSON 格式的字段、ID、数量、长度、HTTPS 封面和凭证门禁，调用方只能拿到标准化副本，提交失败可重试且不会被调用方修改污染。

退出或取消回调的异常正文不会返回 UI，只留下固定的“退出未完成”状态；无论退出成功还是失败，模块都会删除自身可达的 QR、轮询票据和会话引用。合成 canary 测试覆盖成功、重复开始、无效 QR、取消、二维码过期、总超时、普通失败、退出失败、恶意书架字段、迟到结果、提交失败重试及强制本地清理。`force_clear()`只模拟仍有机会执行 Lua 代码时的本地清理，不声称能在 KOReader 进程被直接杀死时运行，也不声称回调、子进程或 Lua 运行时之外没有副本。真实接口、官方二维码载荷、账号、Cookie 和 Kindle 均未接触。

## KOReader 原生内存二维码适配

对目标 KOReader v2026.03 固定源码审计确认，官方 `QRMessage` 使用 `QRWidget`，再由对应 `koreader-base` 的纯 Lua `ffi/qrencode.lua` 生成矩阵并直接绘制到 `BlitBuffer`；`ImageWidget` 收到现成 `image` 时不走文件加载路径。这为“不把授权二维码写入用户分区”提供了实现路径，但仍是源码推断，尚未替代 PW3 上的文件前后对比和关闭回收验证。

审计还发现上游会在 2953 字节后静默截断文本，这对普通分享二维码尚可提示，对授权二维码则会把错误载荷显示成看似正常的 QR。新适配层采用更保守的 2048 字节硬上限，并在构造前拒绝空值、控制字符和超过五分钟的时限；同一时间只显示一个二维码。触摸、按键或超时关闭后会删除文本与回调引用；主动关闭失败时不谎称已消失，而是保留可重试控件句柄并隐藏底层异常正文。合成 canary 测试覆盖构造/显示失败、重复显示、被动关闭、主动关闭、幂等关闭和关闭失败重试。它尚未接入按钮、状态机、Passport 或真实账号。

## 可取消子进程匿名管道门禁

固定审计 KOReader v2026.03 `Trapper:dismissableRunInSubprocess()`与对应 `koreader-base` 后确认，返回值由 POSIX 匿名管道在父子进程间传递，没有命名临时文件。默认复杂结果会经过 `string.buffer`，序列化/解码异常会进入 logger；底层未捕获异常还会把堆栈打印到进程输出。取消使用 `SIGKILL`，子进程无法运行退出接口或任何 Lua 清理。匿名管道因此只解决 IPC 不落盘，不能替任务代码、HTTP 库、Cookie jar、日志或远端会话担保。

新的 `ephemeral_task.lua` 不复用公开 GET 的复杂返回路径：它只接受受信任函数，内部 `pcall` 后只返回一个非空字符串，强制 `task_returns_simple_string=true`，以固定成功/失败帧传输，并在子进程与父进程两侧执行 256 KB 限制。任何异常值、表、空值、超限数据、畸形帧、取消或 Trapper 异常都变成固定中文分类，不调用 `tostring(error)`或 logger。合成 canary 测试证明这些失败路径不会把原始异常放入管道或返回 UI；成功路径按设计仍把受限字符串交给父进程。该阶段真实 HTTP/Cookie 客户端、Passport、账号和 Kindle 均未接入，仍须逐行审计任务自身的输出与文件行为。

## 公开 HTTPS 证书校验补强

2026-08-24 固定审计 KOReader v2026.03 与其 `koreader-base` 依赖时发现，随包 LuaSec 1.3.2 的 `https.lua` 默认配置为 `verify = "none"`；即使开启链验证，该封装也只设置 SNI，没有自动核对证书 SAN 与请求主机名。插件此前直接调用该默认封装，因此源码证据不足以证明公开请求会拒绝中间人证书。这里记录的是源代码层风险，不声称已经观察到攻击或凭证泄露。

官方 Kindle v2026.03 包包含 `koreader/data/ca-bundle.crt`。新实现通过 LuaSec 自定义连接器显式启用 `verify = "peer"` 并引用该 CA 集，握手后读取叶证书 SAN，再按大小写不敏感的精确匹配或仅左侧单标签通配符匹配官方主机名；不回退到 CN。证书缺失、扩展解析失败、SAN 缺失或主机名不匹配都会关闭连接并返回固定中文错误。合成测试同时锁定 CA 路径、禁用旧 TLS 版本的选项和上述失败关闭行为。

该改动尚未在 PW3 发起真实 TLS 握手，也未覆盖设备时钟异常、证书撤销/OCSP、DNS 阶段超时或网络切换。后续敏感请求原型必须复用这条已验证传输边界，不能退回默认 LuaSec 请求封装；这仍不等于真实 Cookie 协议已经实现。

## 端点无关敏感 HTTPS 客户端

在不知道当前官方扫码端点和 Cookie 语义时直接写 Passport 流程，会把猜测固化进安全关键代码。2026-08-24 因此先把 CA/SAN 连接器抽为 `verified_tls.lua`，让公开 GET 和未启用的敏感客户端使用同一实现；原有公开网络合成测试继续覆盖证书链配置、错误 SAN、缺少证书和失败关闭。

新的 `ephemeral_http.lua` 没有真实端点或生产调用。它把主机固定为 `fanqienovel.com`，只接受构造时复制的操作名、精确路径和 GET/POST 白名单，拒绝动态 URL、查询串、未知参数/头、代理和重定向。请求正文、响应和凭证头分别设限；底层异常、状态文本和未列出的响应头不会返回 UI。源码 canary 测试同时禁止 logger、`print()`、`io`、`os` 和原始异常字符串化。

成功正文与白名单允许的 `Set-Cookie` 仍然是敏感内存，客户端不会谎称它们安全或已清零。未来端点任务必须在同一子进程内完成 Cookie 使用、最小书架解析与退出尝试，只把严格标准化的最小 JSON 交给匿名管道。当前还没有 Cookie 合并/过期规则、轮询、退出、账号或 Kindle 证据，主界面的扫码入口仍保持“开发中”。

## 最小书架匿名管道门禁

简单字符串匿名管道消除了默认复杂序列化日志，但并不能阻止未来任务直接 `return cookie` 或返回完整官方响应。`ephemeral_result.lua` 因此复用已经过本地文件实测的严格 JSON 导入器：先拒绝凭证/未知字段并标准化书籍，再只投影 ID、标题、作者、HTTPS 封面、最近章节和位置，删除导出时间等非必要信息。编码后在子进程内立即解码复验，大小继续限制为 256 KB。

`ephemeral_import_task.lua` 把上述编码器固定在 `ephemeral_task.lua` 内侧；父进程收到带帧字符串后再次解码和验证，任何篡改都只返回固定错误且不改变本地书架。合成 canary 证明 Cookie 字段、生产者异常、编码器异常、复验中注入凭证和篡改管道都不会把秘密带到 IPC 或错误提示。主入口没有导入新模块，真实 Passport、响应解析、Cookie、退出和 Kindle 仍未接触。

这一结构门禁无法识别“解析器把 Cookie 值错误塞进合法 title 字段”这类语义错误。未来真实解析器必须从固定响应路径逐字段构造最小 payload，并为字段来源建立独立夹具；不能把原始响应表直接交给门禁后就宣称安全。

## 一次性会话凭证袋收紧

合成失败测试复现了一个内存所有权问题：旧 `Session:authorize()` 直接保存调用方传入的任意表；调用方稍后修改 `credentials.cookie`，会话退出回调实际收到的值也会被替换，未知响应字段同样可能长期挂在会话对象上。

修复后授权入口只复制四个规范字符串：`cookie`、`authorization`、`csrf_token`、`logout_ticket`。Cookie 或 Authorization 至少存在一个；Cookie/Authorization 上限 16 KB，CSRF/退出票据上限 4 KB，所有值拒绝控制字符。独立 `sessionid` 必须放入 Cookie 头而不是成为额外状态字段；任何未知键、非字符串、超限值或 CRLF 注入都会固定失败，并保持原 `qr_pending` 状态供安全重试。

二维码载荷上限同时与内存显示层对齐到 2048 字节，轮询票据限制为 4096 字节，两者也拒绝控制字符。退出回调无论成功、失败还是取消返回，会话都会遍历清空交给回调的内部表，再删除自身引用；因此回调若只保存表引用，之后也读不到字段。canary 测试覆盖这些路径以及调用方原表修改隔离。它不能删除回调另行复制的字符串、调用方原始响应或被 `SIGKILL` 中断时尚未执行的清理，也不证明真实官方字段已经完成映射。

## JSON 解码错误固定化

审计现有文件导入时发现，`Import.decode()` 会把 rapidjson 抛出的对象或返回的错误正文直接 `tostring()` 后交给 UI；`Parser.decode_json()` 对番茄官方响应也有相同行为。解析器错误可能包含输入附近文本，用户误选带 Cookie 的文件或未来私有响应畸形时，原始内容因此可能出现在屏幕或后续日志链。

新增 canary 测试让 rapidjson 分别抛出带自定义 `__tostring` 的异常对象和返回含秘密的错误正文，证明旧路径会触发字符串化。修复后书架文件固定返回“书架 JSON 解析失败、现有书架未改变”，官方响应固定说明格式变化、稍后重试或更新插件、本地数据未改变；异常对象和错误正文都不再读取。

同一审计还发现本地导出会回显 rapidjson 编码异常，搜索会直接拼接官方 `payload.code`。导出现在只报告固定编码失败且不会创建临时文件；搜索只在 `tonumber()` 成功后显示数字码，其他原始状态值被丢弃。合法 JSON、文件导入、导出后复验、数字搜索状态和最小书架 IPC 复验保持原行为。

## 浏览器书架导出边界

浏览器导出原型原先会把顶层异常的 `message` 拼进弹窗，官方非零响应的 `payload.message` 也会进入阶段错误；同时从 `performance` 记录找到的地址只按字符串片段匹配。若官网、扩展或页面脚本返回异常内容，这些路径可能把原始文本显示出来，近似路径或跨域记录也缺少独立失败关闭证据。

修复后脚本只允许 `https://fanqienovel.com/bookshelf` 或尾斜杠页面，并在每次 `fetch` 前重新验证固定官网 origin 与三个精确路径；URL 用户信息、片段、跨域和路径后缀全部拒绝。响应使用严格 UTF-8 流式读取，声明长度和实际累计字节都限制为 2 MB；网络、读取、HTTP、JSON 与服务端业务失败都映射到固定中文分类。只有由脚本内部 `WeakSet` 标记的安全错误会显示固定阶段提示，浏览器或第三方抛出的对象不会被读取正文。封面 URL 也拒绝非 HTTPS、用户信息和片段。

Node 合成测试完成一次三请求下载并解析最终 Blob，确认只输出最小字段和 256 KB 文件边界；凭证 canary 覆盖额外 Cookie、Token、sessionid、CSRF、手机号字段，以及网络异常、HTTP 状态、畸形正文和流读取异常。源码门禁还禁止 `document.cookie`、Web Storage、控制台、`payload.message`、`response.text()` 和原始异常字符串化。这里没有打开真实账号、发送官网请求或验证当前动态字段；测试账号验证前仍只能称为开发工具。

## 公开网络错误固定化

公开 `http.lua` 原先会把无法分类的 LuaSocket/LuaSec 错误原样拼到“网络请求失败”提示中；`networktask.lua` 会对错误结果调用 `tostring()`，主界面的 `with_network()` 还会字符串化任意未捕获异常并显示。即使当前公开 GET 不携带账号凭证，底层异常仍可能含 URL、路径或未来不应展示的上下文，自定义 `__tostring` 也缺少失败关闭证据。

修复后传输层只接收字符串错误用于识别响应过大、超时和证书分类，未分类值统一为可操作的连接失败提示，不回显原值；异常状态码和响应头只接受预期基础类型。网络子进程遇到非字符串错误直接返回固定分类。主界面以弱键表保存由自身创建的用户错误令牌，只有这些令牌能携带经过模块边界的固定说明；其他异常对象不读取正文、不调用 `tostring()`，只显示返回书架、重试或重启 KOReader 的恢复动作。

先添加的失败测试分别证明旧实现会泄漏 socket canary、触发子进程错误对象和主界面异常对象的 `__tostring`。修复后这些 canary 均不可见且元方法调用次数为零，同时原有取消、超时、TLS、HTTP 状态和数据安全说明保持通过。这里没有连接官网或 Kindle，也没有检查真实 KOReader 崩溃日志；这些仍属于后续集中实机矩阵。

## 官方扫码公开脚本快照

2026-08-31 只匿名读取番茄官网 `/bookshelf` 页面与它当时公开加载的 JavaScript，没有调用二维码生成、轮询或退出接口，也没有使用账号、创建会话或保存响应。快照固定了 Web 登录 SDK 的 `aid=2503`、`appName=muye`，以及二维码生成 `/passport/web/get_qrcode/`、轮询 `/passport/web/check_qrconnect/` 和退出 `/passport/web/logout/` 的公开路径名称。

这次审计把“端点未知”缩小为“运行时语义未知”，但不足以安全实现协议。公开脚本没有给出可独立证明的响应字段、状态值、票据有效期、授权主体、Cookie 合并/过期或退出撤销语义。因此没有把路径写进 `ephemeral_http.lua` 的生产策略，也没有连接 UI。候选包测试现在锁定了已证实的应用参数、三个路径与“不得启用真实扫码”边界，避免后续文档或候选包把静态证据误写成可用登录功能。

## 网络框架异常安全复位

联网入口审计确认，添加书籍、搜索、刷新书籍/目录和读取未缓存章节都会经过 `with_network()`，底层请求再经过可取消的 `NetworkTask.get()`。但是旧边界只 `pcall` 了业务回调：若 KOReader 的 `NetworkMgr:runWhenOnline()`、`Trapper:wrap()` 或 `Trapper:reset()` 自身抛错，异常仍可以逃出，任务包装失败后 `network_busy` 还可能一直为真。

失败测试分别向三个框架点抛入带 `__tostring` 的凭证 canary 对象，并复现网络管理器异常直接逃出。修复后，三类框架异常都使用固定中文恢复提示，不字符串化或显示对象，并在返回前清除忙碌状态。KOReader 2026.03 官方源码同时表明，用户在离线 Wi-Fi 提示中放弃时，业务回调不保证执行；因此没有为了防重复点击而在调度前提前持有一个无法可靠释放的忙碌锁。离线重复点击与 Wi-Fi 取消仍保留给集中真机验证。

## 稀疏本地书架恢复

本地设置在写入中断、人工修改或未知故障后可能变成带空洞的 Lua 表。旧加载器对 `books` 和 `chapters` 直接使用 `ipairs`：如果同时存在索引 1 和 3，它会在 2 处停止，既不加载后续数据也不把状态标记为已改变。用户之后只要正常保存一次进度，内存中的截断书架就可以覆盖磁盘原件。

合成失败夹具使用稀疏书籍、稀疏章节和额外键，分别证明旧实现未报告规范化且丢失后续记录。新加载器仅枚举所有正整数索引并按数值排序，将空洞、额外键、无效或重复项标记为需规范化；因此可恢复的后续书籍与章节不会因第一个空洞被舍弃。

审计还发现，启动时若需自动迁移，旧代码先把已规范化状态设为 `persisted_settings`，再将它作为 `.old` 写入；真正的加载前结构没有进入备份。现在 `init()` 在加载书架前复制 `LuaSettings.data`，只在自动规范化时把该原始表作为 previous 交给已有原子写入器。新启动测试同时锁定两本书、后续章节、活跃书 ID 和原始未知字段均进入预期的候选/备份两侧。完全无效的记录仍不能安全猜测，只保留在 `.old` 供人工恢复；真机断电与回退演练仍待集中验收。

## 已移除书籍的缓存决策

书籍页原确认框说“已缓存章节不会同时删除，可稍后单独清理”，但移除后书籍页也从书架消失，设置页没有扫描孤立目录的入口。这不会立即破坏缓存，但把用户留在了说明不存在的操作路径上。

新流程保留“移除不自动删数据”的安全默认：第一个确认只移除书架记录；设置原子保存成功并回到书架后，第二个确认显示移除前读取的缓存数量。只有再次点按“清理缓存”才调用删除；取消时 XHTML 保留，重新添加同一书籍后可复用。无论如何选择，KOReader `.sdr` 阅读位置和未知文件都不在删除白名单内。

同一审计发现，数字书籍目录只经 `lfs.attributes()` 确认为目录；如果它是指向插件根目录外的符号链接，读取、写入、淘汰或清理都可以沿链接访问外部同名文件。现在所有按书目录操作在访问前同时解析缓存根和书籍目录的真实路径，并要求后者精确等于 `real_root/book_id`。合成符号链接夹具证明超出时不读、不写、不调用删除，错误只说明已超出安全范围。这是路径归属门禁，不声称消除检查与实际文件操作之间的所有竞态条件；实机还需验证 `realpath` 差异和两次确认布局。

## 缓存文件链接边界

目录归属修复后继续下钻发现，目录内的数字 XHTML 仍可能单独指向外部普通文件：读取会沿链接打开外部内容，淘汰前的状态检查也会跟随链接。更危险的是同名 `.tmp` 链接，旧写入器直接以 `wb` 打开时可能在验证缓存正文前截断它指向的外部文件。

读取和淘汰现在会重新解析插件缓存根、数字书籍目录及精确 XHTML 文件的真实路径，同时要求目录仍等于 `real_root/book_id`、文件仍等于 `real_directory/item_id.xhtml`，不满足时在打开或删除前固定拒绝。写入前使用不跟随链接的目录项属性检查；任何既有 `.tmp` 文件或链接必须先作为目录项安全移除，再次确认路径不存在后才允许创建。合成测试覆盖外部 XHTML 读取、淘汰、已有临时链接、删除失败、删除后仍占用和检查异常，且异常对象不会被字符串化。这些措施处理正常遗留或外部预置链接，不声称 Lua 用户态的检查与打开之间不存在恶意并发替换窗口，也不替代目标 Kindle 文件系统上的集中验证。

## 原子写入临时链接边界

缓存修复后审计另外两个原子写入器，发现本地书架导出和插件设置也会直接以 `wb` 打开固定的 `.tmp` 路径。正式文件由同目录 `rename` 替换，已有正式路径即使是链接也不会在写入阶段被跟随；但预先存在的临时链接会在复验和改名前先截断其外部目标。

三个写入器现在共用最小的 `safetemporary.lua`：使用不跟随链接的目录项检查，移除任何既有普通文件或链接，再确认同名路径已经消失，之后才允许创建。导出与设置集成测试分别证明链接先被移除；缓存测试继续覆盖检查异常、删除失败和删除后仍占用，并证明原始异常不会进入提示。目标 KOReader v2026.03 固定的 [`koreader-base` 构建清单](https://github.com/koreader/koreader-base/blob/7a46ea3812539083ee25b06f0c81ac58b1356ee0/thirdparty/koreader-lfs/CMakeLists.txt)使用 LuaFileSystem `v1_9_0`，该版本的[模块注册表](https://github.com/lunarmodules/luafilesystem/blob/v1_9_0/src/lfs.c)公开 `symlinkattributes`，因此该调用不是只存在于测试桩中的假接口。用户态检查仍存在恶意并发替换窗口，实机只读、满盘和断电矩阵也仍未完成。

## 缓存根目录信任锚

书籍目录与 XHTML 文件都已相对 `storage.root` 校验，但审计发现这个根本身没有绑定到 KOReader 数据目录。如果整个 `koreader/fanqielite` 是指向其他位置的符号链接，根与其下书籍目录会一起解析到外部，旧检查仍会认为父子关系一致；当数字书籍目录尚不存在时，写入路径甚至可能先在外部执行 `mkdir`，之后才判断书籍目录归属。

`Storage:new()` 现在同时保存 KOReader 数据父目录和逻辑缓存根。任何书籍目录属性读取、创建、缓存读取、淘汰、计数或清理之前，都会重新解析两者，并要求缓存根精确等于 `real_data_dir/fanqielite`；不一致或解析异常时固定拒绝。失败测试把根与书籍目录一起映射到外部，证明修复后不调用读取、删除或 `mkdir`。允许 KOReader 自身的数据目录解析到真实位置，但不允许插件缓存子目录再跳转到其他位置。该检查仍不声称消除验证后的恶意并发替换，也需要目标设备上的真实路径行为验证。

## 可靠的缓存文件清单

书籍页的缓存数量过去只匹配 `数字.xhtml` 文件名，不检查目录项类型或文件归属；同名目录会被计为离线缓存，指向外部的链接也会增加数量。自动淘汰虽然已有真实路径检查，但仍会把同名目录加入候选，之后产生无法删除的警告。状态因此可能与实际可打开、可淘汰的缓存对象不一致。

计数与淘汰现在共用轻量清单：先验证缓存根、数字书籍目录和精确文件真实路径，再要求目录项通过跟随后的类型检查确认为普通文件。同名目录直接忽略，外部链接固定拒绝且不会进入删除候选，属性异常使用固定提示并不字符串化原始对象。该清单不打开或解析最多 12 个 XHTML 正文，避免书籍页状态查询引入整章读取开销；损坏正文仍会在用户实际打开章节时由完整缓存验证器拒绝。

## 拒绝不完整书架导出

本地书架导出原先用 `#library.books` 判断为空，再用 `ipairs` 投影书籍。Lua 对稀疏数组的长度没有稳定保证，`ipairs` 还会在第一个空洞停止；因此索引 1 和 3 同时存在时可能只导出第一本，额外字符串键也会被静默忽略，最终 JSON 仍能通过导入器并显示成功。畸形书籍项还可能在字段投影时抛异常并越过界面错误边界。

导出器现在先枚举全部键，只接受 1 到总数的连续正整数、最多 500 本且每项为表；空洞、额外键、非对象或超限时整次固定拒绝。逐本最小字段投影也在 `pcall` 内执行，异常对象不被字符串化或回显。失败夹具覆盖稀疏数组、混合键、非对象和带恶意索引元方法的书籍；正常两本书导出、严格导入复验与原子替换保持通过。该门禁保护备份完整性，但不替代升级、降级和跨设备恢复实测。

## 导入字段名隔离

严格 JSON 导入虽然会拒绝未知字段和 Cookie、Token、session、CSRF 等凭证字段，但旧错误会把原始键名拼进提示；攻击者或误选文件可以把敏感文本放在键名中，使验证正确拒绝后仍把内容显示到屏幕。递归凭证扫描还会先对任意 Lua 表键调用 `tostring()`，合成异常对象因此能够执行自定义元方法并把 canary 带入后续错误。

字段名规范化现在只接受字符串键，不读取其他对象；凭证字段和白名单错误均返回“字段名和内容未显示”的固定分类。失败测试分别把 canary 放入未知键名、Cookie 键名和自定义 `__tostring` 键对象，证明三者均被拒绝且提示不含 canary、元方法调用次数为零。真实 rapidjson 对象键本应是字符串，这项门禁仍保护直接模块调用、合成任务边界和未来解码器变化；合法文件、原有错误类别与现有书架不变语义保持通过。

## 统一标识符长度

导入器、官方页面解析器、搜索结果、旧设置迁移和缓存路径过去各自只检查“至少 10 位纯数字”，没有最大长度。浏览器导出器也会保留任意长数字字符串。即使导入文件总计限制为 256 KB，单个超长 ID 仍能进入书架设置、菜单状态和目录/文件名；重复 ID 错误还会回显完整值，造成界面膨胀和不必要的数据暴露。

新增 `identifier.lua` 作为 Lua 侧唯一规则：只接受 10–64 字节的纯数字字符串，不把 JSON 数字或 Lua number 隐式转换为 ID。输入链接、官方书籍/目录/章节响应、搜索、本地迁移、JSON 导入、导出复验和缓存路径全部复用该门禁；浏览器工具使用相同范围。重复 ID 提示固定隐藏具体值，超过上限的数字缓存名视为未知文件，不计数、不淘汰、不手动删除。失败测试覆盖六个入口的 65 位 ID，64 位上限远高于当前样本中的 19 位格式，但真实兼容矩阵仍需确认未来官方变化。

## 损坏书架的异常数值修复

Lua 设置文件可通过写入中断、人工修改或其他故障带入 `NaN` 和正负无穷。旧加载器只拒绝目录时间中的 `NaN` 与负数；异常阅读章节、章节序号及添加、更新、最近打开时间仍会进入书架。尤其 `NaN` 与自身不相等，会让设置写入后的重读一致性校验永远失败，用户后续正常阅读也无法把状态修好。

书架加载现在只保留有限数值：无限数组键不会成为书籍或章节；无效阅读章节回到第一章并按现有目录夹紧，异常章节序号回到当前数组位置，异常添加/更新时间使用本次加载时间，异常目录/最近打开时间归零。负时间同样拒绝；字符串数值和被取整的旧索引会标记为需规范化。合成测试覆盖 `NaN`、正负无穷、修复标记和排序可用性。该测试不等于在 Kindle 上人工破坏设置后的启动、`.old` 备份与恢复演练。

## 损坏书架的持久文本清洗

官方响应解析器和 JSON 导入器已经拒绝用户可见文本中的控制字符，但旧设置迁移只做首尾空白与长度处理。人工修改、旧缺陷或损坏设置因此可以把换行、Tab、NUL、DEL 等字符保留到书名、作者、章节标题和导入进度标题；这些字段随后直接用于 KOReader 菜单。封面地址也只检查 `https://` 前缀，没有控制字符或 2048 字节上限，可能让设置和导出持续携带异常值。

书架规范化现在在去除空白前先拒绝全部 NUL、C0 和 DEL，并返回文本是否发生变化。书名与章节标题使用固定安全占位，作者和导入进度标题清空；封面地址还必须不超过 2048 字节并保持 HTTPS，否则完全移除。任一修复都会触发启动规范化写回，第二次加载保持幂等。合成测试覆盖换行、Tab、NUL、DEL、菜单相关字段、封面移除和再次加载；它不替代 Kindle 上人工注入损坏设置后的 `.old` 备份及界面验证。

## 官方书籍链接输入边界

旧 `Parser.book_id()` 用无锚点模式搜索 `fanqienovel.com/page/<数字>` 或任意 `bookId=<数字>`。因此 `evilfanqienovel.com`、把官网字符串塞进第三方路径、用户信息伪装及任意第三方查询参数都可能被当成合法书籍输入。后续请求仍由插件重建为官方 URL，不会访问伪装站点，但界面错误地认可了不可信链接；解析失败的 URL 还会继续进入书名搜索，给新手造成含糊结果。

2026-09-01 匿名打开[番茄官网排行榜](https://fanqienovel.com/rank/1)，确认公开书籍入口仍解析为 HTTPS 的 `/page/<书籍ID>`，章节入口为 `/reader/<章节ID>`；同日匿名 HEAD 还确认 `www.fanqienovel.com/page/<ID>` 以 301 跳回主机。全程未登录、未创建会话或调用账号接口。解析器现在只接受 10–64 位纯数字 ID，或主机精确为 `fanqienovel.com`/`www.fanqienovel.com`、HTTPS、路径精确为 `/page/<ID>` 的链接，并兼容大小写方案/主机、尾斜杠、查询参数和片段。伪装域名、HTTP、端口、用户信息、额外路径、章节链接、任意 `bookId=`、控制字符和 2048 字节超限输入全部固定拒绝；主界面识别到失败的 URL 或超长数字后直接显示官方链接提示，不再发起搜索，像《1984》这样的短数字书名仍使用官网搜索。公开网页快照不能证明所有 App 分享渠道的未来格式，仍需在兼容矩阵中采样。

## 已保存导入位置的修复标记

严格 JSON 导入已经只接受 0–1 的有限 `reading_position`，但设置加载器是另一条恢复边界。旧实现会对已保存位置直接 `tonumber()`：`NaN`、无穷和越界值在内存副本中被省略，数字字符串被转换，却都没有把书架标记为已改变；非对象 `imported_progress` 或无效章节 ID 也会静默丢弃。启动因此把规范化内存误当成磁盘现状，不触发原子写回，异常原值可能每次重启都重新出现，`NaN` 还会破坏后续相等性判断。

加载器现在把导入位置作为独立可选有限数值处理：缺失保持缺失且不制造变更，0–1 number 原样保留，兼容数字字符串转换后标记写回，其他值移除并标记修复。进度不是对象或章节 ID 无效时整个进度对象移除并标记；有效标题继续走既有文本清洗。失败测试覆盖 `NaN`、字符串位置、非对象、无效章节 ID、缺失可选值和修复后幂等；启动集成测试另确认候选设置不含异常位置，而交给 `.old` 写入器的 previous 仍是原始 NaN。它不改变严格导入文件格式，也不替代 Kindle 上损坏设置、真实备份文件和启动提示验证。

## INITIAL_STATE 页面对象边界

公开 HTTP 层已限制响应为 1 MB 且正常只返回字符串，但解析器仍对 `extract_initial_state()` 的参数直接调用 `tostring()`。测试替身、未来复用或内部错误若传入带元方法的对象，该对象可以在解析边界执行代码并伪造一个包含 `window.__INITIAL_STATE__` 的页面；失败 canary 证明旧实现确实调用了 `__tostring` 并接受伪造 JSON。

提取器现在独立要求输入必须是字符串且不超过 1 MB，再开始寻找状态标记和扫描花括号。对象、nil 和超限文本只返回固定中文分类，说明已停止解析且本地数据未改变，不读取对象内容或调用元方法。合成测试锁定 `__tostring` 调用次数为零、canary 不出现在错误中以及超限页面在扫描前拒绝。该双层门禁保护模块边界，不代表已经完成 PW3 上真实 1 MB 临界响应、传输截断或内存压力测试。

## 本地书架查找 ID 边界

统一标识符模块已经要求 ID 必须是 10–64 位数字字符串，但 `Library.find()` 仍先对调用参数执行 `tostring()`。失败 canary 证明，一个带 `__tostring` 的对象可以执行元方法、返回现有书籍 ID 并成功命中；Lua number 也会被旧路径自动接受。该查找函数同时是阅读进度更新和书籍移除的底层入口，因此不能依赖所有未来调用方永远先完成验证。

查找入口现在直接复用 `Identifier.normalize()`，无效类型或格式在遍历书架前返回未找到。测试锁定异常对象不能伪造命中、元方法调用次数为零、数字 ID 被拒绝，同时现有字符串 ID 的查找、刷新、进度和移除用例继续通过。这是内存模块边界加固，不改变持久化格式或当前正常书架数据。

## 启动设置的敏感字段清理

设置持久化层已经拒绝把账号或会话字段写入候选状态和 `.old`，但启动恢复存在相反约束：书架加载器会从内存投影中丢弃未知字段，却不一定把状态标记为已改变，因此仅多出 `sessionid` 等字段的磁盘文件可以长期不重写；如果其他损坏恰好触发迁移，原始设置又会作为 `previous` 被持久化门禁拒绝，导致整次安全清理无法进行。

启动现在完整比较加载前设置与 `state_table()` 白名单投影，任何被投影丢弃的字段都会触发规范化。若原设置含敏感字段，内存中的上一版基线直接采用清洗状态，原子写入器因此只会把同一份安全状态写入 `.old` 和主文件，既不复制敏感原值，也会覆盖可能遗留的旧备份。成功后活动设置不再持有 canary；写入失败时仍使用清洗后的内存书架，并明确提示原磁盘设置可能尚未更新、应暂停账号导入并检查空间或只读状态。合成测试覆盖顶层 `sessionid`、书籍内授权头、成功与原子替换失败；没有读取真实账号或写入 Kindle。

## 公开兼容性采集先导

完整矩阵要求30本书、90个前中末场景全部来自同一个插件候选提交。当前堆叠分支仍在变化，现在把桌面探测直接计入最终矩阵会在候选冻结时失效，也会把未验证缓存写入的解析成功误当成完整证据。因此本轮只执行一组明确标记为不计分的先导审计。

匿名读取官网排行榜中的一本书及其550章目录后，串行读取前、中、末各一章，章节之间等待超过2秒。网页正文经内存中的 JSON 解码和全字节转义管道交给真实 Lua 解析器；没有写临时响应、正文或缓存。书籍和卷目录解析成功，前部公开章节得到2075个可见字符且未知 PUA 为0，中部与末尾都因官方权限标志安全拒绝。三类章节结构指纹一致，未遇到429或验证挑战。结果、限制和匿名 ID/哈希见 [`COMPATIBILITY_PILOT_2026-09-03.md`](COMPATIBILITY_PILOT_2026-09-03.md)；正式矩阵仍必须在冻结提交和目标 Kindle 上重跑。

## 设置页的数据删除后果

“设置与数据”已经包含导入、导出、缓存、隐私和卸载入口，但旧卸载提示只把第2至4项统称为“插件数据”，没有告诉新手删除缓存目录会连同对应 `.sdr` 阅读位置一起消失，删除设置会失去本地书架、目录和插件进度，也没有在完整清理前建议导出。路径本身正确，但缺少不可逆后果说明不满足安全操作要求。

新文案先说明只删除 `fanqielite.koplugin` 就能停用且可保留数据供重装恢复；完整清理前建议导出 JSON 到电脑，再分别说明缓存目录、设置文件和手动导出文件的删除后果。隐私说明也区分默认公开阅读和当前未开放的扫码入口，并固定“不会保存账号登录”。菜单契约测试锁定五个入口顺序和这些关键短语；它仍需在 PW3 上验证长提示分页、字号和新手是否能一次理解。

## 导入目录偏好边界

文件内容验证通过后，插件会记住所选文件的父目录，并在同一次 `save_state()` 中与新书架原子保存；`LuaSettings:saveSetting()` 在这里仅更新内存候选，并没有单独绕过持久化器。但 `state_table()` 旧规则只拒绝 NUL 和 C0，遗漏了 DEL（0x7F），因此带该控制字符的极端目录可以进入设置并影响下次文件选择器显示。

新增的单一目录验证函数同时用于状态投影和导入成功路径：只接受非空、最多1024字节且不含 NUL/C0/DEL 的字符串。异常目录不会调用 `saveSetting()`，从而保留原有安全位置；它也不会让已完成格式验证的书架导入失败。流程测试覆盖 DEL 目录被忽略、书架仍保存并返回首页，以及普通目录继续被记住；状态边界测试另证明 DEL 不会进入持久化候选。

## 等待联网的单请求生命周期

KOReader 2026.03 的 `NetworkMgr:runWhenOnline()` 只保证在成功连接时调用业务回调：用户关闭系统 Wi-Fi 确认、连接失败，或设备已连接局域网但无法访问互联网时，回调都可能不执行。旧实现因此刻意等到回调后才设置 `network_busy`，避免永久上锁；代价是等待阶段反复点按会向网络管理器提交多个回调，连接成功后可能连续执行重复操作。

新流程在进入网络管理器前创建唯一、不可复用的等待令牌，并通过 KOReader UI 调度器设置 50 秒恢复期限。等待期间再次点按只会撤销令牌并说明本地数据未改变，不会提交第二个请求；超时同样清除令牌。网络管理器迟到回调必须先消费仍然有效的同一令牌，取消或超时后的旧回调因此直接返回，不会下载、解析或修改书架。业务任务开始后仍使用既有 `network_busy` 和可取消子进程，两个阶段的取消提示保持分离。

合成测试覆盖等待期重复点按、超时、取消/超时后的迟到回调、恢复后新请求、调度器异常以及原有成功、任务取消和框架异常路径。50 秒取自 KOReader 当前最长约 45 秒的连接检查窗口并留出余量，但系统确认框停留时间也计入其中；超时后用户需要重新点按。这些证据仍不替代 PW3 上关闭系统提示、慢速连接、切换 Wi-Fi、屏幕休眠和真实进度窗口取消测试。

## 瞬时网络失败的原地重试

原有网络提示能说明错误和本地数据状态，但任何失败都只显示普通信息框。新手在临时断网或服务端 5xx 后必须记住原书、原搜索或原章节，再从页面层级中重新发起；反过来，如果对登录墙、证书、404 或限流一律添加重试，又会诱导没有恢复条件的重复请求。

公开 HTTPS 层现在只为连接失败、网络超时、传输不完整和 HTTP 5xx 返回固定的 `retryable` 分类。429、安全验证、证书失败、登录/授权、404、重定向、响应过大、空响应和其他状态不带该分类。可取消子进程只接受精确字符串并转换成布尔值，父进程也只接受布尔 `true`；未知值和带元方法对象不会被读取或字符串化。主动取消使用独立 `cancelled` 分类，永远不弹重试。

主界面的可信用户错误令牌同时携带固定消息与布尔重试资格。可重试错误在任务包装和忙碌状态复位后显示“重试 / 返回”，选择重试会在下一次 UI tick 重新执行完全相同的用户操作；解析变化、缓存写入、设置保存和 KOReader 打开失败仍走各自恢复建议。合成测试覆盖四类可重试传输、5xx、取消、登录边界、未知分类 canary、同操作回调复用和每次 Trapper 复位。它不替代 PW3 上按钮尺寸、墨水屏残影、断网后重新连接、连续失败和返回页面体验。

## 当前章节限定的可选阅读器动作

首页和书籍详情已有可见上一章/下一章，但正文内切章仍要重新打开插件。KOReader 2026.03 的 Dispatcher 允许插件注册阅读器动作，手势管理可由用户自行绑定；直接把动作指向 `active_book_id` 却不安全，因为用户可能已经打开普通 EPUB、另一插件书籍，或插件最近状态与屏幕文档不一致。

插件现在注册“番茄小说：上一章 / 下一章”两个仅出现在阅读器动作列表中的动作，不自动创建、覆盖或要求任何手势。执行时先读取 KOReader 当前文档路径，只接受插件缓存根下精确的 `<书籍ID>/<章节ID>.xhtml`；随后要求书籍仍在本地书架、章节仍在当前目录，并通过 `Storage:cached_chapter()` 的真实路径归属和完整 XHTML 校验。只有全部成立才计算相邻索引并复用现有 `open_chapter()`，所以未缓存目标章仍使用统一联网、取消、超时和错误边界。

动作不依赖最近阅读书籍，普通 EPUB/PDF、其他插件文档、已移除书籍、过期目录、伪造路径、缺失/损坏缓存、缓存检查异常及首末章都在打开前停止。独立测试还固定 Dispatcher 元数据必须是 `reader=true` 且不能泄漏到 general 列表，并证明异常详情不会显示。设置页说明手势完全可选且所有功能有按钮兜底；仍须在 PW3 验证动作可见性、实际绑定、当前文档路径、缓存/联网切章、触摸冲突和残影。
