# 从零到一

## 起点

这个项目源于一个很直接的问题：已经能在 Kindle Paperwhite 3 上运行 KOReader，能否也用它阅读番茄小说？

第一步不是编写界面，而是确认技术边界。调研发现，番茄小说的官方阅读网页包含服务端渲染的章节状态；目录也可以由官方网页接口取得。但此前看到的非官方实现会依赖第三方聚合正文源，这不符合本项目希望保持的范围。

因此，0.1.0 确立了几条原则：

- 只请求 `fanqienovel.com` 官方网页。
- 不登录，不接触账号 Cookie 或个人书架。
- 不批量下载整本书。
- 不绕过付费、登录或章节锁定。
- 无法可靠解析时明确失败，不把乱码写入缓存。

## 第一个原型

原型验证了三件关键事情：

1. 书籍页面可以提取书名和书籍 ID。
2. 官方目录响应可以整理成 KOReader 可操作的章节列表。
3. 公开章节中的 PUA 字符可按当前映射还原成正常文字。

插件采用很小的分层：`http.lua` 负责受限的网络请求，`parser.lua` 负责页面和章节解析，`pua.lua` 负责字符映射，`storage.lua` 只管理插件自己的缓存，`main.lua` 连接 KOReader 菜单和阅读器。

## 第一次完整自检

在准备 0.1.0 时，自检发现并修复了三个会影响真实使用的问题：

- 中文长度最初按 UTF-8 字节数统计，可能误判短预览；现改为按 Unicode 字符计数。
- 目录定位最初调用了 KOReader 中不存在的方法；现使用 2026.03 实际提供的分页接口。
- 网络底层抛出异常时可能无法恢复全局超时；现保证请求结束后复位。

最终验证覆盖 Lua 5.1 语法、核心离线测试、官方书籍页、目录、公开章节和登录墙页面。桌面端验证通过后生成了第一个安装包。

## 第一次 Kindle 实机验证

2026-08-16，0.1.0 被复制到 Kindle Paperwhite 3（固件 5.16.2.1.1）上的 KOReader 2026.03。KOReader 正常启动，工具菜单出现“番茄小说（实验版）”，离线说明页面可以打开。连接 Wi-Fi 后，测试书籍的书名与当时最新的 88 章目录正常显示；打开第一章后，正文完整、无乱码，KOReader 翻页正常。

这次结果把项目状态从“桌面端可行性验证”推进到了“单台 PW3 实机验证通过”。它仍不是对所有 Kindle 型号、KOReader 版本或未来网页结构的兼容性保证。

## 多书本地书架

稳定版候选的第一项改造从本地数据开始，而不是先做账号登录。原因是登录属于可选能力，不能成为日常阅读体验的前提。

新书架以带版本号的数据结构保存多本书，每本书独立记录目录、最后阅读章节、添加时间、目录更新时间和最近打开时间。首次启动新版时，0.1.0 的单书设置会自动迁移；同时保留并同步旧字段，使用户仍可降级回 0.1.0。刷新目录时优先按章节 ID 找回原阅读章节，避免目录前方新增章节后进度错位。

删除边界被刻意拆成两个动作：“从书架移除”不删除缓存，“清理缓存”不删除书籍和进度，且都需要用户确认。缓存清理只接受数字书籍 ID，并只删除插件目录内符合数字章节名规则的 XHTML 与临时文件。

## 网络边界审计

审计发现原型虽然设置了 20 秒总超时，但自定义响应接收器没有实际检查总耗时；慢速分块响应可能持续阻塞界面。修复后，接收器同时检查累计时间和 1 MB 大小限制，并保证请求成功、失败或底层异常时都恢复 KOReader 的全局网络超时。

网络模块现在只接受 `https://fanqienovel.com/` 地址，明确禁用重定向，并检查声明的响应长度。超时、证书、重定向、权限、限流、页面不存在和服务端错误会转换成可操作的中文提示，同时说明本地数据没有改变。

## 安全 JSON 导入

浏览器文件导入先实现 Kindle 端的严格接收边界。插件只显示并接受名为 `fanqielite-bookshelf.json` 的文件，读取前限制为 256 KB，解析后要求固定格式版本、连续书籍数组、最多 500 本、字符串 ID、字段长度和 0 到 1 的阅读位置。

导入采用字段白名单，并递归拒绝 Cookie、Token、session、CSRF、密码、手机号和授权头等凭证字段。全部书籍通过验证后才显示新增与更新数量；用户再次确认后才写入本地书架。导入已有书籍时保留其目录、缓存和本地阅读进度；新书首次打开时再从番茄官方地址获取目录。

文件读取边界的后续审计发现，`io.open` 的原始系统错误会进入界面，文件定位、读取或关闭抛异常时还可能越过“现有书架没有改变”的失败说明。现在打开、末尾定位、大小验证、回到开头、完整读取和关闭均使用 `pcall` 与固定中文分类；只有读取字节数与预先确认大小一致且文件安全关闭后才进入 JSON 解码。合成 canary 覆盖打开、大小定位、回到开头、读取、关闭和主界面非字符串错误，修复后不显示 canary 且不调用 `__tostring`。该证据不替代 Kindle 上误选、拔线、只读或损坏文件的集中真机验证。

## 搜索功能的失败实验

2026-08-16 检查了番茄官网当前使用的 `/api/author/search/search_book/v1`。未登录的直接只读请求返回 HTTP 200 但正文为空；在官方搜索页执行相同关键词时，页面出现滑块验证，结果保持为空。

这意味着“在 Kindle 中直接按书名搜索”目前没有经过验证的稳定官方路径。项目不会绕过验证码，也不会为了填补入口而接入第三方搜索源。界面应继续诚实说明当前只支持官方链接或 ID；搜索只有在找到合法、稳定且可在 Kindle 上完成的官方流程后再实现。

## 缓存完整性边界

章节缓存不能只凭文件存在就交给 KOReader 打开。插件现在会先检查大小、固定 XHTML 结构、完整结尾和 XML 非法控制字符；损坏缓存会被拒绝，并在不改变书架与阅读进度的前提下尝试联网重新获取。

写入仍采用同目录临时文件和原子改名，同时开始检查 `write` 与 `close` 两个阶段。磁盘写满、只读或关闭文件失败时会删除未完成的临时文件，保留原有正式缓存，并提示用户检查空间或只读状态。

后续错误边界审计发现，缓存创建、写入、关闭、改名、读取、目录遍历和删除仍可能把底层系统错误拼入用户提示，异常对象还可能触发 `__tostring`。现在这些操作都封装在 `pcall` 或不读取异常内容的 best-effort 清理中，只返回固定中文阶段或经程序统计的成功/失败数量。创建、写入、关闭或改名失败会清理 `.tmp`；读取失败不会把损坏或不可确认的文件交给 KOReader；清理仍只接受数字书籍 ID，并只删除 `数字.xhtml` 与 `数字.xhtml.tmp`，不会删除同目录其他文件。

合成 canary 覆盖属性读取、目录打开与迭代、缓存创建/写入/关闭/改名、章节读取、自动淘汰、手动部分清理和主界面非字符串错误。修复前原始异常会传播或出现在提示中；修复后 canary 不可见且 `__tostring` 调用次数为零。

缓存持久性随后复用 KOReader 的 `fsyncOpenedFile()`：临时正文完整写入后先同步文件，关闭后重新读取并执行同一套 XHTML 大小、结构、控制字符和完整结尾校验，只有通过才原子替换正式缓存。同步、关闭或复验失败都清理 `.tmp` 并保留原正式文件；替换后调用 `fsyncDirectory()`，但与设置写入相同，目录同步发生在替换之后，只能作为 best-effort。故障注入覆盖同步异常、重读截断和目录同步异常，不把异常对象送入提示。这里仍不声称已通过断电级验收，也未在只读或满盘的 Kindle 文件系统上完成集中验证。

## 设置写入完整性

核对 [KOReader 2026.03 的 `LuaSettings`](https://github.com/koreader/koreader/blob/v2026.03/frontend/luasettings.lua) 与 [`util.writeToFile()`](https://github.com/koreader/koreader/blob/v2026.03/frontend/util.lua#L1141) 后确认，`LuaSettings:flush()` 不会把底层写入失败返回给调用方，而底层也未检查 `write()` 和 `close()` 的结果。插件不能用 `flush()` 的返回值证明书架或进度已经落盘。

因此插件设置改为先生成临时 Lua 设置文件，调用 KOReader 的 `fsyncOpenedFile()`、关闭并重读校验后，再原子替换正式文件；每次替换前用同样流程保存上一版 `.old`。写入、同步、关闭、重读校验或改名任一步失败时，本次内存修改会回滚，界面会说明设置未保存及检查空间/只读状态。网络操作的用户提示也不再展示 Lua 调用栈。

后续错误边界审计发现，上述步骤虽然能阻止失败文件替换正式设置，但 `io.open`、`write`、`fsync`、`close` 和 `os.rename` 的底层错误仍会被 `tostring()` 后送往界面；序列化器返回非字符串对象时，拼接设置文本也会触发元方法。现在创建和改名也置于 `pcall` 内，序列化结果必须是字符串，各失败阶段只返回固定分类，临时文件清理采用不读取异常的 best-effort。主界面只接受字符串设置错误，否则使用固定“没有返回可安全显示的错误说明”，再恢复上一版内存状态。

合成 canary 覆盖序列化对象、创建抛错、同步/关闭异常对象、改名抛错和主界面异常返回；修复前测试会显示 canary 或调用 `__tostring`，修复后调用次数为零，正式设置逐项保持旧值且无 `.tmp` 残留。这里仍不声称已经解决断电窗口：正式文件内容在改名前已 fsync 并复验，但目录 fsync 发生在替换后且只是 best-effort，仍需在目标 Kindle 文件系统上单独验证。

## 真正可取消的网络任务

KOReader 2026.03 官方的 [`Trapper:dismissableRunInSubprocess()`](https://github.com/koreader/koreader/blob/v2026.03/frontend/ui/trapper.lua) 会让 UI 保持响应，并在用户点按取消时终止和回收子进程。插件只把无副作用的官方 HTTP GET 放进子进程；解析、书架修改、缓存写入和设置保存仍留在主进程，并且只在完整响应返回后发生。

因此取消书籍信息、目录或章节请求时，不会留下临时下载、半份响应或内存里的书架修改。并发点击会被“已有网络操作”门禁拒绝。该机制仍需在 PW3 上验证点按响应、强制退出和 Wi-Fi 切换。

## 解析安全变体

章节与书籍 ID 现在统一要求至少 10 位数字，并拒绝响应 ID 与请求不一致。锁定判断同时覆盖布尔 `true`、数字 `1` 和字符串 `"1"`/`"true"`，避免接口序列化方式变化后把受限章节误当成公开正文。

PUA 解码前的 UTF-8 扫描补齐了续字节、过长编码、代理区和超过 U+10FFFF 的边界。无效 UTF-8 与未知 PUA 都会在生成缓存前安全拒绝；合法四字节字符保持不变。自动测试同时覆盖畸形目录、书籍/章节 ID 不一致、数字和字符串锁定标志。

## 缓存清理的部分失败

清理缓存过去只统计删除成功的文件，删除失败会被静默忽略，界面仍可能显示“已清理”。现在目录打开/遍历错误会直接失败；若只删除了部分文件，插件会分别报告成功数、失败数和首个系统错误，并明确未删除缓存仍可使用、书架和进度没有改变。

删除白名单仍只允许数字章节名的 `.xhtml` 与 `.xhtml.tmp`。目录里即使出现未知文件也不会删除；因此未知文件导致空目录移除失败时不会把它当成缓存清理失败。

## 本地书架安全导出与数据设置

插件现在可把本地书架导出为与严格导入器相同的版本 1 JSON。生成内容只使用书籍白名单字段，并在写入前通过导入验证；同目录临时文件完成写入和同步后会再次解析验证，随后原子替换固定文件名并做最终复验。失败不会改动书架、缓存或插件设置，也不会把部分写入报告成成功。

文件系统错误边界的后续审计发现，导出创建、写入、同步、关闭、重读、校验和改名仍会把底层错误拼入用户提示，`io.open`、读取或 `os.rename` 抛异常时还可能越过导出失败说明。现在这些阶段都使用 `pcall` 与固定中文分类，临时文件删除为不读取异常的 best-effort；主界面也只接受字符串错误，否则显示固定安全回退。合成 canary 覆盖创建、写入、同步、关闭、清理、重读、改名和非字符串 UI 错误，修复后不显示 canary 且不调用其 `__tostring`。这不替代只读、满盘或断电真机验证，也不改变导出文件位于 Kindle 用户盘根目录、可被 USB 读取的隐私边界。

导出当前章节时只使用插件确实记录的章节 ID 与标题，不虚构章节内百分比；从已验证文件导入且尚未加载本地目录的合法百分比可以原样迁移。“设置与数据”同时集中显示导入/导出、缓存与隐私边界，以及仅供用户手动执行的完整卸载路径，插件本身不执行自动删除。

2026-08-19 在同一台 PW3 导出当前 2 本书架。因根目录已有测试 JSON，确认框明确显示将安全“替换”；操作完成后插件报告已安全导出 2 本，无错误或闪退。导出文件为 455 字节，插件自身的严格导入器复验通过并返回 2 本；顶层只有 `books`、`exported_at`、`format`、`version`，书籍字段集合只有作者、当前章节 ID 与标题、书籍 ID 和书名。递归检查未发现凭证字段，也没有正文、缓存字段、`.tmp` 或 macOS 元数据残留；插件设置与导出前备份逐字节一致。真实 JSON 只保留在本地私有备份中，未提交仓库。

## 官方浏览器验证挑战

2026-08-17 对番茄官网当前公开搜索流程的只读审计确认：网页使用 `/api/author/search/search_book/v1`，但匿名直连可能返回 HTTP 200、空正文和 `Bdturing-Verify` 滑块验证响应头。使用插件现有浏览器 User-Agent 仍会触发；搜索页本身也不服务端输出结果。Kindle 无法可靠完成该网页滑块，因此插件不会尝试绕过或复用验证令牌，书名搜索暂不能据此宣称稳定可用。

网络层现在会识别官方验证响应头而不记录或展示其值，明确提示“官方安全验证、Kindle 无法显示、稍后重试或粘贴官网链接”；其他无挑战头的空响应也会安全拒绝。两种情况都不会进入解析、缓存或书架写入阶段。

在此边界上，书名/作者搜索采用有限的“尽力而为”模式：只访问上述番茄官方 HTTPS 接口，只请求第一页 10 条结果，并严格验证连续数组、数量、字符串书籍 ID、标题和作者字段。无效条目不会进入书架；选中结果后仍复用既有书籍页与目录验证流程。官网正常返回时新手可直接搜索加入，出现滑块挑战时则明确回退到粘贴官网链接，不能把该能力描述成所有网络下都可用。

搜索响应状态码的后续审计发现，直接 `tonumber()` 会把 NaN、无穷、小数和科学记数法字符串当成可显示的服务代码，响应字段变为对象时不同 Lua 实现的行为也不应被信任。现在只接受 32 位有符号整数或最多 11 位的十进制整数字符串；其余类型统一显示固定“官方搜索暂时不可用”。合成测试覆盖对象 canary、NaN、正负无穷、小数和科学记数法，均不回显原值或调用 `__tostring`。

## KOReader 数据目录实机核对

2026-08-17 在上述 PW3 的用户盘核对确认，`DataStorage:getDataDir()` 对应 `koreader/`，现有章节缓存与 KOReader 的相邻 `.sdr` 阅读位置数据均位于 `koreader/fanqielite/`。运行时代码原本已通过 `DataStorage:getDataDir() .. "/fanqielite"` 使用正确位置；本次仅修正文档与卸载界面的错误路径提示，不迁移或删除任何数据。

## 多书书架升级实机回归

2026-08-17 将当前开发栈写入同一台 PW3 前，先完整备份旧版插件与 `fanqielite.lua`/`.old` 设置，并逐文件校验新版运行文件。KOReader 重启后正常进入文件管理器，没有报错或闪退；插件首页显示“我的本地书架”，旧版单书《迟来的余光》成功迁移，书籍详情保留“继续阅读”、上下章、目录和刷新入口。

迁移前设置本来就是 `current_index = 1`，迁移后仍显示继续阅读第 1 章。目录包含 87 条记录，但标题编号跳过第 55 章并以“第 88 章”结束，所以界面显示 87 章不是迁移丢失。打开继续阅读时直接复用原有第 1 章缓存，正文完整、无乱码且没有缓存损坏提示；KOReader 同时恢复到该 XHTML 上次保存的章节内位置。这证明本次升级保留了旧书架、章节缓存和相邻 `.sdr` 阅读位置，但尚不代表其他设备、其他书籍或联网刷新已经通过。

## 导入阅读位置的一次性恢复

JSON 格式允许携带当前章节内 0 到 1 的 `reading_position`，但旧实现只保存该值，从未交给 KOReader。现在目录首次加载后，插件只在打开匹配章节且 `DocSettings:hasSidecarFile()` 确认没有本机阅读记录时，通过 KOReader 的 `GotoPercent` 事件应用一次，然后在安全保存插件设置时消费该值。

导入已有本地目录的书不会附加外部进度；曾移除后重新导入的书如果仍保留 sidecar，也以本机位置为准并丢弃导入位置。打开错误章节不会提前消费，保存失败会恢复上一次持久状态。该行为只解释并应用已经通过 JSON 边界验证的标准化位置，不读取、改写或删除 KOReader sidecar。

## 兼容矩阵完成门禁

现有兼容证据工具原本只统计记录数和正确率，即使样本全来自同一长度档、每本只测一个位置或完全没有安全拒绝场景，也可能给出看似良好的摘要。现在普通模式仍允许查看部分采集进度，`--require-complete` 则强制验证不少于 30 本/90 场景、五档 5/5/8/7/5 配额、至少 12 本完结与 18 本连载、每本互不重复的前中末三处、同一插件候选提交、男频/女频及出版或版权受限覆盖、公开正文至少 95% 正确，以及短预览、登录墙、锁定、畸形响应、章节 ID 不一致和未知 PUA 各至少一个安全拒绝场景。

所有非公开或未知 PUA 场景只有在结果为安全拒绝、未写缓存、未显示乱码且给出可操作提示时才算通过。新书/较早作品和结构哈希来源无法从匿名白名单字段自动证明，继续保留人工复核；限流也不得为满足类型而主动触发。自动门禁只证明证据文件满足口径，真实 30 本/90 场景尚未采集，不能提前宣称兼容率达标。

## 去正文解析夹具与实体边界

原有解析测试把状态表直接写在单个测试文件中，难以持续扩展，也没有证明卷目录、平铺目录、ID 目录和安全拒绝场景使用同一套稳定口径。首批独立夹具现在只使用虚构 ID 与重复生成的合成文字，不保存真实书名、作者或完整正文；逐项记录预期通过结果或必须出现的可操作拒绝原因。

新增失败夹具发现两个会破坏安全失败原则的缺口：目录列表混入非法章节或重复 ID 时，解析器过去会静默保留部分结果；未知 PUA 或非法 Unicode 通过数字 HTML 实体表示时，可以绕过实体解码前的字符检查。现在选中的目录结构只要包含无效条目、重复 ID 或错误容器类型就整体拒绝，避免用截断目录覆盖本地状态；十进制和十六进制实体先按 XML 合法字符范围验证，实体解码后再次检查 UTF-8 与 PUA。合法实体及已知 PUA 仍可正常解码，完整测试通过。真实网页矩阵尚未采集，因此不能把夹具通过解释为兼容率已经达标。

字段类型审计随后发现，书籍/章节 ID、标题、作者、目录序号、正文字数和正文曾使用隐式 `tostring()` 或 `tonumber()`；更严重的是，`needPay` 或 `isChapterLock` 变成对象时会被当作 false，可能把未知权限状态误判为公开。现在 ID 只接受数字字符串，存在的文本与正文只接受字符串，序号和字数只接受有限非负整数，权限只接受 nil/false/0/`"0"`/`"false"` 与 true/1/`"1"`/`"true"`。未知权限、对象正文或畸形字数都会在 PUA 解码和 XHTML 生成前拒绝。合成 canary 证明对象书名与正文不会触发 `__tostring`；这些夹具仍不能替代真实网页结构矩阵。

用户可见文本边界继续与本地导入格式对齐：书名和章节标题最多 300 字节，作者最多 150 字节，并在去除首尾空白前拒绝 NUL、换行、制表和其他控制字符，避免网页字段伪造多行菜单或膨胀设置。正文单独限制为 1 MB，允许 XML 合法的 Tab、LF 和 CR，拒绝 NUL、DEL 及其他 C0 控制字节；非法正文会在 PUA 和 HTML 处理前停止。夹具覆盖超长标题、作者换行、目录标题换行、正文 NUL、正文超限及合法正文空白，不能替代真实长章节兼容验证。

目录容器审计还发现，Lua `ipairs` 会在第一个空洞停止并忽略字符串键，因此稀疏卷列表、稀疏卷内章节或混入额外键的 ID 列表可能被截断后错误接受。现在被选中的外层卷、直接卷数组、卷内 `chapterList`、平铺 `chapterList` 和 `allItemIds` 都必须只含从 1 开始的连续整数键；合法卷对象在其 `chapterList` 之外的元数据不受影响。夹具证明任一空洞或混合键都会整体拒绝，不会返回部分目录供 `Library.upsert()` 覆盖本地状态。

正文清理过去只移除全小写 `<script>` 与 `<style>`，混合大小写块会在通用去标签后留下内部文本。足够长的脚本或样式文本因此可能让实际只有几个字的预览页越过 500 字门槛。现在完整块以大小写无关、标签名 frontier 边界明确的规则移除，避免误匹配 `<scripture>` 等名称；清理后仍残留的 script/style 开闭标签视为未闭合异常并整体拒绝。合成夹具覆盖带属性的混合大小写脚本、多行样式和未闭合脚本，均不能贡献可见正文长度。

同一长度门禁无法模拟浏览器 CSS：`hidden`、`aria-hidden="true"`、`display:none` 或 `visibility:hidden` 容器中的长文本过去也会在去标签后被计算为可见正文。插件现在逐个检查标签的小写副本，只有明确隐藏属性或声明才整体拒绝，不尝试猜测嵌套布局；普通正文单词 hidden、`class="not-hidden"`、`display:inline` 和 `visibility:visible` 不受影响。四类隐藏夹具均在长度统计和缓存前停止，但 CSS class、外部样式表和复杂渲染仍只能在真实矩阵中识别。

HTML 注释同样不可见，但通用 `<[^>]+>` 模式会在注释正文内部第一个 `>` 提前结束，剩余长文本过去可参与长度统计。现在标准 `<!-- … -->` 注释在其他标签处理前完整移除；清理后残留任一开始或结束边界都作为未闭合/畸形注释拒绝。夹具覆盖包含 `>` 的长注释、未闭合注释和经 `&lt;`/`&gt;` 转义后应当可见的注释文字，后者在实体解码后仍正常显示。

同一个通用去标签模式还会把引号属性中的合法 `>` 当成标签终点：长属性尾部可能泄露成正文并凑够公开长度，位于该字符之后的真实 `hidden` 属性也不会进入旧的标签检查。正文清理现在逐字节寻找引号之外的结束符，再解析实际属性名和值；标签属性整体移除，真实隐藏属性仍安全拒绝，而普通 `title` 值中的 hidden 单词保持兼容。夹具分别证明长属性不能满足正文长度、引号后的隐藏属性会被识别，以及长公开正文不会夹带属性尾部。

开始真实兼容采集前复核证据口径时发现，旧工具把任意 `result=success` 且“无乱码”的公开响应计为正确，即使同条记录明确写着缓存未保存、可见正文不足 500 字、只达到官方声称字数的一小部分或仍含未知 PUA。95% 门禁因此可能高估实际可读性。公开正确记录现在必须同时满足解析器的两条可见长度门槛、未知 PUA 为零且缓存已经保存；四类单记录夹具和一组低于 95% 的完整矩阵夹具锁定了该口径。该检查只能验证记录内部一致性，仍不能替代采集过程与原始公开页面的人工核对。

矩阵规范原先要求结构哈希不可来自完整正文，却没有标准生成方法。新的 `--fingerprint` 离线模式从标准输入读取最多 2 MB 的 JSON，只将排序后的字段名、值类型及数组中不同的元素结构组成规范模型再计算 SHA-256；字符串内容、数字/布尔值和数组长度不会进入模型。测试证明完全不同的正文、ID 和真假值在字段结构相同时得到同一指纹，新增字段会改变指纹，畸形输入不会回显 canary；深度和节点数也有固定上限。工具仍无法证明记录填写者实际使用了该模式，真实证据入库前必须人工复核来源并删除私有原始响应。

首次使用流程审计确认首页已经按产品顺序提供扫码、搜索/添加和文件导入三个入口，但未开放的扫码入口过去只显示泛化“开发中”，没有告诉新用户账号是否被请求，也没有指出可立即使用的替代路径。现在该提示明确说明当前版本未发起账号授权、未请求或保存登录信息、已有本地书架不受影响，并列出搜索/添加与文件导入。新的首页契约测试同时锁定标题、三个入口顺序和回调连接；实际文字布局、触摸体验与 5 分钟完成时间仍须陌生新手真机验证。

## 自动缓存淘汰失败提示

章节成功原子写入后，插件会把每本书的缓存限制在 12 个，但旧实现忽略了自动淘汰的目录遍历和删除结果。只读文件或目录错误因此可能让缓存数量持续增长，界面却没有任何提示。测试还证明，当设备时间异常使新文件时间戳看起来更旧时，单纯按修改时间排序可能误删刚写好的当前章节。

现在淘汰器会显式保护本次写入的章节，时间相同时使用稳定路径顺序，并分别统计成功数和失败数，不再显示底层系统错误。新章节已经完整写入时不会因旧缓存删不掉而被丢弃或阻止阅读；阅读器打开后会说明“章节已保存”、书架与当前章节未损坏，并建议稍后手动清理或检查空间与只读状态。缓存说明也改为“最多 12 个、优先清理较早写入”，不再错误声称按最近打开顺序淘汰。自动测试覆盖目录不可读、全部删除失败、异常时间戳保护和警告透传；真机布局及只读/满盘行为仍待集中验证。

## 候选测试包与 5 分钟安装路径

直接下载 GitHub 源码压缩包会额外套一层带分支名的目录，新手若原样复制，KOReader 无法在预期路径找到 `_meta.lua`。仓库过去也只有一句安装说明，没有验证包内是否混入测试、工具、设置或缓存，更没有升级备份、失败判断和安全回退步骤。

新的候选包构建只复制明确白名单：运行 Lua、许可证、README、安装指南、变更记录，以及 README 直接引用的书架格式、兼容矩阵、质量计划和安全审计文档，避免包内说明出现断链。生成结果固定为单层 `fanqielite.koplugin/`，不超过 1 MB，文件名和 `BUILD-INFO.txt` 绑定 Git 提交，并配套 SHA-256；默认拒绝从未提交工作区生成候选包。自动测试会核对每一个包内路径、提交身份，解压后再次检查 Lua 5.1 语法，同时拒绝任何意外文件。中文指南按 0–1、1–3、3–4、4–5 分钟拆分目录检查、复制、安全弹出、重启和加入第一本书，并提供升级备份、官网验证、TLS、预览/锁定、回退和卸载说明。脚本只在本地或 CI 生成测试产物，不创建 Release、不上传、不打标签；真正的 5 分钟门禁仍须陌生新手实测。

## 扫码威胁模型与设置硬门禁

真实扫码实现前先完成独立威胁模型，明确 QR 载荷、轮询票据、Cookie、CSRF、Token、授权头和退出票据都是瞬时凭证；本地只允许保存最小书架数据。模型不声称 Lua 字符串可以可靠清零，也不把官方退出成功当作本地安全前提。它要求在显示最终导入确认前完成退出尝试并清除凭证引用，同时把二维码真机行为、HTTP/Cookie 子任务、当前官方授权主体、会话有效期和退出语义列为重新验证前的 No-Go 条件。

自动失败测试同时发现，虽然当前 `state_table()`不会投影插件根部的瞬时会话、`Library.import_books()`也只复制书籍白名单字段，但底层 `Persistence.write()`过去仍会忠实写入调用方误传的嵌套会话字段。现在候选状态和上一版备份在任何文件创建前都会递归拒绝账号、二维码、票据、Cookie、CSRF、Token、请求头等字段；错误只返回固定分类，不回显字段值。普通书名中出现 Cookie/Token 文字不会误拒绝。合成 canary 测试覆盖状态投影、现有/新书导入、主设置和 `.old` 拒绝；真实账号、Passport 请求和二维码仍完全未接触。

## 端点无关的一次性会话核心

在确认真实 Passport 协议前，先把不依赖接口的生命周期做成独立纯 Lua 模块。模块不接 UI、HTTP 或本地书架，只负责单实例运行代号、五分钟总时限、二维码过期、授权后取数、退出尝试、待确认数据和提交结果；任何迟到的旧运行结果都会被当前运行代号拒绝。待确认书架必须再次经过现有 JSON 格式的字段、ID、数量、长度、HTTPS 封面和凭证门禁，调用方只能拿到标准化副本，提交失败可重试且不会被调用方修改污染。

退出或取消回调的异常正文不会返回 UI，只留下固定的“退出未完成”状态；无论退出成功还是失败，模块都会删除自身可达的 QR、轮询票据和会话引用。合成 canary 测试覆盖成功、重复开始、无效 QR、取消、二维码过期、总超时、普通失败、退出失败、恶意书架字段、迟到结果、提交失败重试及强制本地清理。`force_clear()`只模拟仍有机会执行 Lua 代码时的本地清理，不声称能在 KOReader 进程被直接杀死时运行，也不声称回调、子进程或 Lua 运行时之外没有副本。真实接口、官方二维码载荷、账号、Cookie 和 Kindle 均未接触。

## KOReader 原生内存二维码适配

对目标 KOReader v2026.03 固定源码审计确认，官方 `QRMessage` 使用 `QRWidget`，再由对应 `koreader-base` 的纯 Lua `ffi/qrencode.lua` 生成矩阵并直接绘制到 `BlitBuffer`；`ImageWidget` 收到现成 `image` 时不走文件加载路径。这为“不把授权二维码写入用户分区”提供了实现路径，但仍是源码推断，尚未替代 PW3 上的文件前后对比和关闭回收验证。

审计还发现上游会在 2953 字节后静默截断文本，这对普通分享二维码尚可提示，对授权二维码则会把错误载荷显示成看似正常的 QR。新适配层采用更保守的 2048 字节硬上限，并在构造前拒绝空值、控制字符和超过五分钟的时限；同一时间只显示一个二维码。触摸、按键或超时关闭后会删除文本与回调引用；主动关闭失败时不谎称已消失，而是保留可重试控件句柄并隐藏底层异常正文。合成 canary 测试覆盖构造/显示失败、重复显示、被动关闭、主动关闭、幂等关闭和关闭失败重试。它尚未接入按钮、状态机、Passport 或真实账号。

## 可取消子进程匿名管道门禁

固定审计 KOReader v2026.03 `Trapper:dismissableRunInSubprocess()`与对应 `koreader-base` 后确认，返回值由 POSIX 匿名管道在父子进程间传递，没有命名临时文件。默认复杂结果会经过 `string.buffer`，序列化/解码异常会进入 logger；底层未捕获异常还会把堆栈打印到进程输出。取消使用 `SIGKILL`，子进程无法运行退出接口或任何 Lua 清理。匿名管道因此只解决 IPC 不落盘，不能替任务代码、HTTP 库、Cookie jar、日志或远端会话担保。

新的 `ephemeral_task.lua` 不复用公开 GET 的复杂返回路径：它只接受受信任函数，内部 `pcall` 后只返回一个非空字符串，强制 `task_returns_simple_string=true`，以固定成功/失败帧传输，并在子进程与父进程两侧执行 256 KB 限制。任何异常值、表、空值、超限数据、畸形帧、取消或 Trapper 异常都变成固定中文分类，不调用 `tostring(error)`或 logger。合成 canary 测试证明这些失败路径不会把原始异常放入管道或返回 UI；成功路径按设计仍把受限字符串交给父进程。该阶段真实 HTTP/Cookie 客户端、Passport、账号和 Kindle 均未接入，仍须逐行审计任务自身的输出与文件行为。

## 公开 HTTPS 证书校验补强

2026-08-24 固定审计 KOReader v2026.03 与其 `koreader-base` 依赖时发现，随包 LuaSec 1.3.2 的 `https.lua` 默认配置为 `verify = "none"`；即使开启链验证，该封装也只设置 SNI，没有自动核对证书 SAN 与请求主机名。插件此前直接调用该默认封装，因此源码证据不足以证明公开请求会拒绝中间人证书。这里记录的是源代码层风险，不声称已经观察到攻击或凭证泄露。

官方 Kindle v2026.03 包包含 `koreader/data/ca-bundle.crt`。新实现通过 LuaSec 自定义连接器显式启用 `verify = "peer"` 并引用该 CA 集，握手后读取叶证书 SAN，再按大小写不敏感的精确匹配或仅左侧单标签通配符匹配官方主机名；不回退到 CN。证书缺失、扩展解析失败、SAN 缺失或主机名不匹配都会关闭连接并返回固定中文错误。合成测试同时锁定 CA 路径、禁用旧 TLS 版本的选项和上述失败关闭行为。

该改动尚未在 PW3 发起真实 TLS 握手，也未覆盖设备时钟异常、证书撤销/OCSP、DNS 阶段超时或网络切换。后续敏感请求原型必须复用这条已验证传输边界，不能退回默认 LuaSec 请求封装；这仍不等于真实 Cookie 协议已经实现。

## 端点无关敏感 HTTPS 客户端

在不知道当前官方扫码端点和 Cookie 语义时直接写 Passport 流程，会把猜测固化进安全关键代码。2026-08-24 因此先把 CA/SAN 连接器抽为 `verified_tls.lua`，让公开 GET 和未启用的敏感客户端使用同一实现；原有公开网络合成测试继续覆盖证书链配置、错误 SAN、缺少证书和失败关闭。

新的 `ephemeral_http.lua` 没有真实端点或生产调用。它把主机固定为 `fanqienovel.com`，只接受构造时复制的操作名、精确路径和 GET/POST 白名单，拒绝动态 URL、查询串、未知参数/头、代理和重定向。请求正文、响应和凭证头分别设限；底层异常、状态文本和未列出的响应头不会返回 UI。源码 canary 测试同时禁止 logger、`print()`、`io`、`os` 和原始异常字符串化。

成功正文与白名单允许的 `Set-Cookie` 仍然是敏感内存，客户端不会谎称它们安全或已清零。未来端点任务必须在同一子进程内完成 Cookie 使用、最小书架解析与退出尝试，只把严格标准化的最小 JSON 交给匿名管道。当前还没有 Cookie 合并/过期规则、轮询、退出、账号或 Kindle 证据，主界面的扫码入口仍保持“开发中”。

## 最小书架匿名管道门禁

简单字符串匿名管道消除了默认复杂序列化日志，但并不能阻止未来任务直接 `return cookie` 或返回完整官方响应。`ephemeral_result.lua` 因此复用已经过本地文件实测的严格 JSON 导入器：先拒绝凭证/未知字段并标准化书籍，再只投影 ID、标题、作者、HTTPS 封面、最近章节和位置，删除导出时间等非必要信息。编码后在子进程内立即解码复验，大小继续限制为 256 KB。

`ephemeral_import_task.lua` 把上述编码器固定在 `ephemeral_task.lua` 内侧；父进程收到带帧字符串后再次解码和验证，任何篡改都只返回固定错误且不改变本地书架。合成 canary 证明 Cookie 字段、生产者异常、编码器异常、复验中注入凭证和篡改管道都不会把秘密带到 IPC 或错误提示。主入口没有导入新模块，真实 Passport、响应解析、Cookie、退出和 Kindle 仍未接触。

这一结构门禁无法识别“解析器把 Cookie 值错误塞进合法 title 字段”这类语义错误。未来真实解析器必须从固定响应路径逐字段构造最小 payload，并为字段来源建立独立夹具；不能把原始响应表直接交给门禁后就宣称安全。

## 一次性会话凭证袋收紧

合成失败测试复现了一个内存所有权问题：旧 `Session:authorize()` 直接保存调用方传入的任意表；调用方稍后修改 `credentials.cookie`，会话退出回调实际收到的值也会被替换，未知响应字段同样可能长期挂在会话对象上。

修复后授权入口只复制四个规范字符串：`cookie`、`authorization`、`csrf_token`、`logout_ticket`。Cookie 或 Authorization 至少存在一个；Cookie/Authorization 上限 16 KB，CSRF/退出票据上限 4 KB，所有值拒绝控制字符。独立 `sessionid` 必须放入 Cookie 头而不是成为额外状态字段；任何未知键、非字符串、超限值或 CRLF 注入都会固定失败，并保持原 `qr_pending` 状态供安全重试。

二维码载荷上限同时与内存显示层对齐到 2048 字节，轮询票据限制为 4096 字节，两者也拒绝控制字符。退出回调无论成功、失败还是取消返回，会话都会遍历清空交给回调的内部表，再删除自身引用；因此回调若只保存表引用，之后也读不到字段。canary 测试覆盖这些路径以及调用方原表修改隔离。它不能删除回调另行复制的字符串、调用方原始响应或被 `SIGKILL` 中断时尚未执行的清理，也不证明真实官方字段已经完成映射。

## JSON 解码错误固定化

审计现有文件导入时发现，`Import.decode()` 会把 rapidjson 抛出的对象或返回的错误正文直接 `tostring()` 后交给 UI；`Parser.decode_json()` 对番茄官方响应也有相同行为。解析器错误可能包含输入附近文本，用户误选带 Cookie 的文件或未来私有响应畸形时，原始内容因此可能出现在屏幕或后续日志链。

新增 canary 测试让 rapidjson 分别抛出带自定义 `__tostring` 的异常对象和返回含秘密的错误正文，证明旧路径会触发字符串化。修复后书架文件固定返回“书架 JSON 解析失败、现有书架未改变”，官方响应固定说明格式变化、稍后重试或更新插件、本地数据未改变；异常对象和错误正文都不再读取。

同一审计还发现本地导出会回显 rapidjson 编码异常，搜索会直接拼接官方 `payload.code`。导出现在只报告固定编码失败且不会创建临时文件；搜索只在 `tonumber()` 成功后显示数字码，其他原始状态值被丢弃。合法 JSON、文件导入、导出后复验、数字搜索状态和最小书架 IPC 复验保持原行为。

## 浏览器书架导出边界

浏览器导出原型原先会把顶层异常的 `message` 拼进弹窗，官方非零响应的 `payload.message` 也会进入阶段错误；同时从 `performance` 记录找到的地址只按字符串片段匹配。若官网、扩展或页面脚本返回异常内容，这些路径可能把原始文本显示出来，近似路径或跨域记录也缺少独立失败关闭证据。

修复后脚本只允许 `https://fanqienovel.com/bookshelf` 或尾斜杠页面，并在每次 `fetch` 前重新验证固定官网 origin 与三个精确路径；URL 用户信息、片段、跨域和路径后缀全部拒绝。响应使用严格 UTF-8 流式读取，声明长度和实际累计字节都限制为 2 MB；网络、读取、HTTP、JSON 与服务端业务失败都映射到固定中文分类。只有由脚本内部 `WeakSet` 标记的安全错误会显示固定阶段提示，浏览器或第三方抛出的对象不会被读取正文。封面 URL 也拒绝非 HTTPS、用户信息和片段。

Node 合成测试完成一次三请求下载并解析最终 Blob，确认只输出最小字段和 256 KB 文件边界；凭证 canary 覆盖额外 Cookie、Token、sessionid、CSRF、手机号字段，以及网络异常、HTTP 状态、畸形正文和流读取异常。源码门禁还禁止 `document.cookie`、Web Storage、控制台、`payload.message`、`response.text()` 和原始异常字符串化。这里没有打开真实账号、发送官网请求或验证当前动态字段；测试账号验证前仍只能称为开发工具。

## 公开网络错误固定化

公开 `http.lua` 原先会把无法分类的 LuaSocket/LuaSec 错误原样拼到“网络请求失败”提示中；`networktask.lua` 会对错误结果调用 `tostring()`，主界面的 `with_network()` 还会字符串化任意未捕获异常并显示。即使当前公开 GET 不携带账号凭证，底层异常仍可能含 URL、路径或未来不应展示的上下文，自定义 `__tostring` 也缺少失败关闭证据。

修复后传输层只接收字符串错误用于识别响应过大、超时和证书分类，未分类值统一为可操作的连接失败提示，不回显原值；异常状态码和响应头只接受预期基础类型。网络子进程遇到非字符串错误直接返回固定分类。主界面以弱键表保存由自身创建的用户错误令牌，只有这些令牌能携带经过模块边界的固定说明；其他异常对象不读取正文、不调用 `tostring()`，只显示返回书架、重试或重启 KOReader 的恢复动作。

先添加的失败测试分别证明旧实现会泄漏 socket canary、触发子进程错误对象和主界面异常对象的 `__tostring`。修复后这些 canary 均不可见且元方法调用次数为零，同时原有取消、超时、TLS、HTTP 状态和数据安全说明保持通过。这里没有连接官网或 Kindle，也没有检查真实 KOReader 崩溃日志；这些仍属于后续集中实机矩阵。
